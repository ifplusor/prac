# 轴一：责任分配 + AI 能力

> 这是prac 的两个根轴。绝大多数「不顺手」的手感问题，都能回溯到这两根轴上的错配，而不是某个具体开关。

## 问题：现有 harness 的默认分工，让双方都接到自己最不擅长的活

主流 harness 的隐含分工是：**人 = 定目标 + 全程监督 + 判对错；AI = 稳定执行。**

两边其实都错位了：

- **人**被要求一次性、完整地把意图说清（prompt engineering），且持续盯一个比人类注意力快得多的过程。但人是靠**行动里逐步发现意图**的；让一个「先想清楚再动手」的物种去当「边动边看的监督者」，它天生不胜任。
- **模型**被要求带稳定状态、长期自持地执行。但模型没有稳定状态——它是 next-token 预测器，不是带记忆的认知主体。让它「持续一个目标跑几小时、还能自我校验」，恰是它架构上最弱的一环。

**手感差的根源往往不是某个开关，而是人和 AI 之间的交接边界设计得糟。** 控制感好不好，只是这个边界的地表症状。

## 重排主张

- **AI 只负责有界认知**：感知当下、提出选项、生成、做局部转换。每个都是可验证的短单元，不做长期自持。
- **人负责意图 + 高杠杆处的判断 + 真实校验**，只在值得介入的决策点出现。
- **harness 负责账本**：维护外部、持久、可核实的事实账户——哪个文件确实改了、测试真的过了、这个调用真的发生了。**这是 harness 的事实源，不信任模型的自我报告。** 模型说的「我觉得成了」从来不是 truth，harness 的 ground-truth ledger 才是。

## 验证环（中心器官）

不是「模型说完成就算完」，而是：

```
模型产出一个工作单元
  → harness 独立对着现实校验（编译？测试？符合约定？）
  → 校验通过才入账
```

很多 harness 做到了这一步，但卡在下一步——**把错误喂回去无脑重试**。真正该做的是给错误做**分类**：

| 错误类型 | 特征 | 正确应对 |
| --- | --- | --- |
| 机械性 | 局部 bug、语法/格式错 | 修完重试（重试 token） |
| 方向性 | 这条路本身就走错了 | 重新审方案（重审方案），不是再试一次 |
| 能力缺口 | 不是模型不行，是 rig 没给够东西 | 是我们要修的机会，不是结论 |

「重试 token」和「重审方案」是两回事。一个 harness 是只会原地打转，还是真在用模型思考，差别就在它如何处理「这次失败属于哪一类」。

## AI 能力轴：把假天花板和真天花板分开

当你说「AI 能力问题」时，常撞到的是两类混杂：

- **真天花板**：当前模型确实做不到。
- **假天花板**：其实是这套 rig 没让模型触碰到它够得着的东西（缺工具、缺上下文、缺权限）。

实践中「AI 做不到 X」绝大多数是假天花板。自建工具最值钱的地方之一，就是能系统地去猎这些假天花板，并把真天花板测准——你终于能诚实地说「这件事到底卡在哪」。

## 三个真正的设计分叉

1. **校验姿态**：验证越硬越可信，也越慢越贵。机械但高频的校验做默认；判断性的事交还给人。但「机械 vs 判断」的边界划在哪，就是这套工具的性格。
2. **外置状态 vs 流程流畅**：账本外置让它可靠，但外置多了就变回行政开销。哪个点它不再是负担、而是真的有用的「产品」，得靠用起来感受。
3. **决策点怎么设计**：把人减到「只在关键时刻出现」很吸引人，但也容易漏掉真需要他的事。怎样的打断才是**对的分歧点**、在**对的时机**出现——目前基本没有好答案，很可能正是最值得做的差异化。
