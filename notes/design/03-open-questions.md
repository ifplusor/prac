# 未解决的设计问题

> 这些是框架已经点出、但还没想透的问题。其中第一个被认为是**立身之本**。

## 1. 如何呈现一个「待裁决的决策空间」（立身之本）

agent 现在把「做决策的空间」直接坍缩成「改文件」，人被迫在结果里找 bug。要改成「先摊开决策空间给人选」，需要回答：

- 一个**候选决策**用什么结构承载？（选项、代价、推荐、验证计划）
- 什么时机摊开：一次性摊全部，还是逐层展开？
- 怎么避免变成「填表式追问」（foundation/dual_agent 里 Secretary 明确反对的坏对话）？——它应该是对话式、自然的，不是表单。

## 2. 人用什么直觉判别一个候选决策该不该采纳

这是工具的立身之本。它决定「审查是主界面」到底怎么落地：

- 人类评判一个决策时，到底在用哪些信号？口味、长期后果、可维护性、风险？
- 这些信号能不能被**显式化**，让 agent 知道该在哪几个维度上举证，好让人判断？
- 还是说，人的判断本质上是**整体性、不可分解的**（一眼觉得不对），那 harness 该做的只是把它**及时、低成本地触发**出来，而不是试图拆解它？

> 这条我倾向后者：人的判断是一眼的东西，harness 的价值是把「该触发判断的时刻」和「让判断容易做出的上下文」给到位，而不是逼人把判断写成可复述的规则。

## 3. 校验姿态：机械 vs 判断的边界

验证越硬越可信、也越慢越贵。默认是「机械但高频的校验」（跑测试、编译、diff 对齐约定），判断性的事交还给人。但：

- 这个边界具体划在哪？
- 一次「方向性错误」vs 一次「机械错误」，如何自动分类（见 01 的错误分类表）？

## 4. 外置状态 vs 流程流畅

账本外置让它可靠，但外置多了就变回行政开销。哪个点它不再是负担、而是真的有用的产品？需要实际用起来感受。

## 5. 决策点/打断设计

把人减到「只在关键时刻出现」很吸引人，但也容易漏掉真需要他的事。

- 怎样的打断是**对的分歧点**、在**对的时机**出现？
- 打断是「请求裁决」还是「告知分歧」？中断太多会烦，太少会漏，如何校准？

## 6. 长程任务与该模式的矛盾

当前行业方向在增强长程自主，而这可能牺牲「有深度人类参与」的协作模式。但模型能力与 harness 未必准备好了。这个张力要怎么处理：

- 长程的「探索」（拓宽选项空间）交给 agent 是值得的；
- 长程的「承诺」（收敛到对的东西）必须留给人。

这两者的边界在哪里？
