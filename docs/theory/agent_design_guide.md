# Agent 设计指南

> **本文档提供 Agent 系统的设计模式、操作规范与反模式参考。**
>
> 理论基础见 [agent_foundations.md](agent_foundations.md)

## 高级模式（Meta Patterns）

> **以下模式建立在基础能力之上，是多种能力的协同应用。**

### 1. 自适应任务编排（Adaptive Task Orchestration）

**依赖能力**：任务编排系统 + 验证反馈机制 + 执行控制系统

**模式描述**：

- **分解策略**：将大目标拆为内聚的子目标，显式维护优先级、依赖关系与验收标准
- **执行模式**：通过子 Agent 并行或串行完成子任务，聚合结果时验证完整性
- **重启委托**：将目标、约束、成功条件持久化后，启动全新 Agent 实例执行，避免上下文污染
- **动态调整**：根据中间验证结果调整后续任务优先级和执行策略

### 2. 学习型执行循环（Learning Execution Loop）

**依赖能力**：持久化记忆系统 + 验证反馈机制 + 自我演化系统

**模式描述**：

- **反思循环**：每轮执行后记录观察 → 归纳有效策略与反模式 → 应用于下轮执行
- **经验沉淀**：可泛化的策略固化为程序记忆（工具/脚本）或提示模板库，形成可复用的能力
- **持续优化**：基于历史成功/失败案例调整规划策略和工具选择
- **能力迁移**：将一个领域的成功模式迁移到类似场景

### 3. 鲁棒性执行（Robust Execution）

**依赖能力**：验证反馈机制 + 执行控制系统 + 持久化记忆系统

**核心关注**：错误的检测、诊断与恢复

**模式描述**：

- **多层验证**：关键节点强制测试或对账（类型检查、单元测试、端到端验证）
- **快速失败**：误差检测后立即触发重规划或回滚，防止误差级联
- **根因分析**：失败时追溯决策链，识别是工具问题、推理问题还是目标模糊
- **优雅降级**：无法完成全部目标时，返回部分可用结果并说明限制

### 4. 长流程状态管理（Long-Running State Management）

**依赖能力**：执行控制系统 + 智能检索系统 + 任务编排系统

**核心关注**：跨越时间和上下文边界的状态延续

**模式描述**：

- **Checkpoint/Resume**：长流程执行时周期性保存状态快照，失败后从检查点恢复
- **状态压缩**：定期总结已完成步骤，压缩为精简的上下文描述，释放窗口空间
- **目标追踪**：外部化 Todo list 和进度追踪，防止目标漂移
- **分段执行**：超过阈值的流程强制拆分为多个阶段，每阶段独立验证

### 5. 取消与中断（Cancellation & Interruption）

**依赖能力**：执行控制系统 + 持久化记忆系统

**核心关注**：安全终止执行流程并保持系统一致性

**模式描述**：

- **安全点设计**：在可中断的边界（如工具调用前后）检查取消信号
- **状态清理**：中断时回滚未完成的原子操作，释放占用的资源
- **进度保留**：已完成的步骤结果持久化，支持后续从断点恢复
- **中断原因记录**：区分用户主动取消、超时、错误触发等不同中断类型

### 6. 多 Agent 协调（Multi-Agent Coordination）

**依赖能力**：任务编排系统 + 持久化记忆系统 + 智能检索系统

**核心关注**：多个 Agent 实例间的信息共享与冲突避免

**模式描述**：

- **上下文隔离**：每个子 Agent 拥有独立的上下文窗口，避免相互污染
- **共享状态协议**：通过持久化存储（而非内存）交换信息，保证一致性
- **任务边界明确**：委托时清晰定义输入、输出和成功标准，减少歧义
- **结果聚合**：父 Agent 负责整合子 Agent 结果，处理冲突和不一致

### 7. 能力退化（Graceful Degradation）

**依赖能力**：验证反馈机制 + 工具抽象层

**核心关注**：工具或能力不可用时的适应性行为

**模式描述**：

- **能力探测**：执行前检测可用工具和资源，动态调整执行策略
- **替代路径**：为关键能力准备备选方案（如：API 不可用时使用本地缓存）
- **能力边界声明**：明确告知用户当前受限的能力及其影响
- **部分完成**：在能力受限时尽可能完成可达成的部分，而非完全失败

## 人机协作边界

> **Agent 应最大化自主性，但在特定情况下必须或可以引入人类协助。**

### 必须请求人类介入

| 场景             | 原因                   | 示例                                             |
| ---------------- | ---------------------- | ------------------------------------------------ |
| **破坏性操作**   | 不可逆后果需人类授权   | 删除生产数据、发布到公网、大规模文件修改         |
| **能力边界**     | Agent 确认无法完成     | 需要物理世界操作、需要人类专有权限、超出知识范围 |
| **高风险决策**   | 决策错误代价巨大       | 架构重大变更、安全相关配置、财务操作             |
| **歧义无法消解** | 多次尝试仍无法理解意图 | 需求描述矛盾、缺少关键信息且无法推断             |

### 可以请求人类协助（但应克制）

| 场景         | 克制原则       | 正确做法                                        |
| ------------ | -------------- | ----------------------------------------------- |
| **信息不足** | 先尝试自主获取 | 先搜索、读取文档、推断，失败后再询问            |
| **方案选择** | 先形成建议     | 提供 2-3 个方案及利弊分析，请人类决策           |
| **验证困难** | 先自动化验证   | 先写测试、执行检查，无法自动化时再请人工验证    |
| **效率考虑** | 评估时间成本   | 若自主完成需 10x 时间，可请求协助，但需说明原因 |

### 求助的正确姿态

1. **说明已尝试的方法**：展示自主探索过程，而非直接提问
2. **提供上下文**：给出相关信息，减少人类理解成本
3. **明确需要什么**：是决策、信息、还是操作授权
4. **提供默认选项**：如果可能，建议一个默认行动方案

## 常见反模式（Anti-patterns）

> **以下是 Agent 设计和使用中常见的错误模式及其修正方法。**

| 反模式                              | 问题描述                                     | 正确做法                                              |
| ----------------------------------- | -------------------------------------------- | ----------------------------------------------------- |
| **在循环中调用 LLM 处理列表**       | Token 浪费严重，触发速率限制，执行缓慢       | 使用批处理工具或一次性传递整个列表让 LLM 生成处理逻辑 |
| **依赖 LLM 记住前 N 轮对话的细节**  | 上下文窗口外的内容遗忘，或幻觉补全缺失细节   | 显式注入关键上下文到当前 prompt，或使用检索系统       |
| **单个 Prompt 塞入 5+ 个不同目标**  | 注意力稀释，优先级混乱，部分目标被忽略       | 拆分为多次独立调用，或明确标注优先级和验证标准        |
| **全量替换文件内容**                | 大文件消耗大量 tokens，易引入无关修改        | 使用 unified diff 或精确定位的局部修改                |
| **长流程无状态追踪**                | 目标漂移，中间失败无法恢复，执行黑盒         | 使用 Todo list、Checkpoint 和进度日志                 |
| **忽略工具调用结果，相信 LLM 陈述** | 幻觉导致错误判断（如"文件已创建"但实际失败） | 始终验证工具返回值，以执行结果为准                    |
| **过度依赖 LLM 进行数值计算**       | 算术错误频发，复杂计算结果不可靠             | 使用代码执行工具（Python REPL）进行计算               |
| **无限制递归调用子 Agent**          | 堆栈溢出、成本爆炸、无法收敛                 | 设置最大递归深度，使用迭代替代递归                    |
| **关键操作无验证循环**              | 一次失败即放弃，无重试或人工确认机制         | 实现验证 → 反馈 → 重试循环，关键步骤人工确认          |
| **混用多种编程语言/工具无统一抽象** | 工具冲突，上下文混乱，难以维护               | 定义统一的工具协议（如 ToolProvider），封装差异       |
