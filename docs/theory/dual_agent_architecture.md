# 双 Agent 架构：意图澄清与任务执行分离

> **本文档探讨将用户意图澄清与任务执行分离为两个角色的架构设计。**

**核心设计决策**：

| 决策         | 说明                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| **命名**     | Secretary（秘书）负责对话与调度，Executor（执行者）负责任务执行              |
| **架构定位** | 两者是系统架构中的组件/角色，可共享底层基础设施，也可有专门实现              |
| **角色隐喻** | Secretary 如同秘书：接待用户、理解需求、安排执行、汇报结果                   |
| **可分解性** | 每个角色可进一步拆分为更小的子组件（如 Executor 可拆分为规划、执行、验证等） |

## 问题陈述

### 用户请求的类型谱系

用户请求可以从两个维度理解：

**维度一：请求的性质**

| 类型       | 特征                       | 示例                          |
| ---------- | -------------------------- | ----------------------------- |
| **执行类** | 需要产生副作用（改文件等） | "把这个函数改成异步的"        |
| **分析类** | 需要调查、评估、诊断       | "这个架构有什么问题？"        |
| **咨询类** | 需要建议、比较、决策支持   | "该用 Redis 还是 Memcached？" |
| **解释类** | 需要理解、学习、澄清概念   | "这个设计模式是什么意思？"    |
| **探索类** | 开放式思考、头脑风暴       | "我在想要不要重构..."         |
| **社交类** | 寒暄、感谢、闲聊           | "谢谢！""今天效率真高"        |

**维度二：请求的深度**

| 深度     | 特征                     | 示例                                 |
| -------- | ------------------------ | ------------------------------------ |
| **浅层** | 基于当前上下文可快速回答 | "这个函数是做什么的？"（文件已打开） |
| **中层** | 需要少量额外信息收集     | "这个模块的主要依赖有哪些？"         |
| **深层** | 需要大量调研、多文件分析 | "分析整个项目的架构问题"             |

**处理方式矩阵**

```text
              浅层              中层              深层
           ─────────────────────────────────────────────
执行类   │  Executor (同步)   Executor (异步)  Executor (异步)
分析类   │  Secretary 回应    Secretary/降级   Executor 调研
咨询类   │  Secretary 回应    Secretary/降级   Executor 调研
解释类   │  Secretary 回应    Secretary 回应   Executor 调研
探索类   │  对话协作          对话协作         对话 → 调研
社交类   │  简短回应          —                —
```

> **Secretary/降级**：Secretary 先尝试，发现超出能力时降级委托 Executor

**同步 vs 异步调用**：

- **同步**：浅层执行任务，Secretary 等待 Executor 完成后再回复用户
- **异步**：中/深层任务，Secretary 立即返回，用户可继续对话，完成后通知

**关键洞察**：

- 不是所有请求都需要变成"任务"
- 同一类型的请求，深度不同，处理方式不同
- 很多请求会在对话中从浅层演化到深层
- **Secretary 不执行副作用**——所有执行类请求都派发 Executor，浅层同步、深层异步
- **Secretary 可尝试后降级**——中层分析/咨询类先尝试，失败则委托 Executor

### 用户表达的固有特征

| 特征         | 说明                       | 示例                                |
| ------------ | -------------------------- | ----------------------------------- |
| **模糊性**   | 意图不精确，缺少关键细节   | "帮我写个脚本" → 什么语言？做什么？ |
| **不完整性** | 一轮对话无法表达全部需求   | 第一轮提需求，后续补充约束          |
| **渐进性**   | 用户自己也在思考中明确需求 | 边看边想，逐步细化                  |
| **噪音**     | 包含寒暄、感谢、闲聊等     | "谢谢！对了，还有一个问题..."       |
| **隐含假设** | 用户认为显而易见的背景知识 | "就像之前那个项目一样"              |

### 当前 Agent 面临的挑战

1. **目标冲突**：同时要"理解用户"和"执行任务"，注意力分散
2. **上下文污染**：对话内容与执行内容混杂，噪声累积
3. **状态混乱**：难以区分"还在澄清"还是"已经执行"
4. **回溯困难**：执行中发现理解错误，需要大量上下文回溯

## 架构设计

### 核心思想

将 Agent 分为两个角色，各司其职：

```text
┌─────────────────────────────────────────────────────────────────┐
│                         用户                                    │
│                   (看到的是一个 always on call 的助手)          │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 自然语言对话（同步）
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│                   Secretary (对话层)                            │
│                                                                 │
│  职责：                                                         │
│  • 理解用户意图、多轮对话澄清                                   │
│  • 过滤噪音（寒暄、感谢等）                                     │
│  • 识别任务边界、生成任务规格                                   │
│  • 管理进行中的任务、向用户报告进度                             │
│  • 处理用户的中断、取消、优先级调整                             │
│                                                                 │
│  特点：                                                         │
│  • Always available —— 用户随时可以对话                         │
│  • 维护任务队列和状态                                           │
│  • 是用户看到的"那个助手"                                       │
└────────────┬───────────────────────────────────┬────────────────┘
             │                                   │
             │ 提交任务（同步/异步）             │ 接收报告
             ▼                                   │
┌────────────────────────────────────────────────┴────────────────┐
│                       Task Queue (任务队列)                     │
│                                                                 │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐            │
│   │ Task 1  │  │ Task 2  │  │ Task 3  │  │  ....   │            │
│   │ running │  │ pending │  │ pending │  │         │            │
│   └─────────┘  └─────────┘  └─────────┘  └─────────┘            │
│                                                                 │
└─────────────────────────────┬───────────────────────────────────┘
                              │ 分发任务
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
┌──────────────────┐ ┌──────────────────┐ ┌──────────────────┐
│  Executor        │ │  Executor        │ │  Executor        │
│   (实例 1)       │ │   (实例 2)       │ │   (实例 N)       │
│                  │ │                  │ │                  │
│  执行 Task 1     │ │  空闲/待命       │ │  空闲/待命       │
└──────────────────┘ └──────────────────┘ └──────────────────┘
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │ 执行报告（异步）
                              ▼
                    ┌──────────────────┐
                    │   Report Queue   │
                    └──────────────────┘
```

### 同步与异步调用

Secretary 与 Executor 支持两种调用模式：

| 模式     | 适用场景                 | 用户体验                           |
| -------- | ------------------------ | ---------------------------------- |
| **同步** | 浅层执行任务（快速完成） | Secretary 等待，用户得到即时反馈   |
| **异步** | 中/深层任务（需要时间）  | Secretary 立即返回，用户可继续对话 |

### 异步解耦的核心价值

| 特性               | 说明                                             |
| ------------------ | ------------------------------------------------ |
| **Always On Call** | Secretary 始终响应用户，不因 Executor 忙碌而阻塞 |
| **并行执行**       | 多个 Executor 实例可同时处理不同任务             |
| **弹性伸缩**       | 根据负载动态增减 Executor 实例                   |
| **容错隔离**       | 单个 Executor 失败不影响其他任务和用户对话       |
| **优先级管理**     | Secretary 可以调整任务队列优先级                 |

### Secretary 的任务管理职责

Secretary 不仅是对话层，还是**任务调度中心**：

```markdown
## Secretary 管理的状态

1. **对话上下文**
   - 当前对话历史
   - 用户画像和偏好

2. **任务列表**
   - 进行中的任务（task_id, 状态, 开始时间）
   - 等待中的任务
   - 已完成的任务（最近 N 个）

3. **通知队列**
   - 待告知用户的执行结果
   - 需要用户澄清的问题
```

### 用户交互场景

**场景 1：提交任务后继续对话**

```text

Agent：好的，我开始分析了。这可能需要几分钟。
       你可以继续问我其他问题，分析完成后我会告诉你。
用户：对了，项目文档在哪里？
Agent：项目文档在 docs/ 目录下，主要包括...
       [1分钟后]
       销售趋势分析完成了！总体呈上升趋势，Q3 增长最快...
```

**场景 2：多任务并行**

```text
用户：帮我做三件事：1) 跑测试 2) 生成文档 3) 检查代码风格
Agent：收到，我会并行处理这三个任务：
       • 测试运行中...
       • 文档生成中...
       • 代码检查中...
       [陆续完成]

```

**场景 3：任务中断**

```text
用户：帮我重构整个 utils 模块
Agent：好的，开始重构...
用户：等等，先停一下，我想先确认一件事
Agent：已暂停重构任务。你想确认什么？
用户：算了，不重构了，改成只提取公共函数
Agent：明白，我取消之前的重构任务，改为提取公共函数...
```

### 通信格式设计原则

**核心原则：元数据 + 结构良好的自然语言正文**

过度结构化的问题：

- 复杂任务难以塞进预定义字段
- 理解结构化内容需要依赖 schema 知识
- LLM 更擅长处理自然语言

因此采用：

- **元数据**：少量必要的结构化字段（ID、状态、时间戳）
- **正文**：使用 Markdown 等结构良好的文本格式，自由表达

### Task Specification（任务规格）

采用 YAML front matter + Markdown body 的形式：

```markdown
---
task_id: task-20260123-001
created_at: 2026-01-23T10:30:00Z
priority: high
---

# 任务：实现用户登录功能

## 目标

为现有的 Flask 应用添加用户登录功能，支持用户名密码认证。

## 背景

- 项目使用 Flask + SQLAlchemy
- 已有 User 模型，包含 username 和 password_hash 字段
- 前端使用 Jinja2 模板

## 成功标准

1. 用户可以通过 /login 页面登录
2. 登录后 session 中保存用户信息
3. 有基本的错误提示（用户名不存在、密码错误）
4. 包含 "记住我" 选项

## 约束

- 不要修改现有的 User 模型
- 使用 Flask-Login 扩展
- 密码验证使用 werkzeug.security

## 相关文件

- `app/models/user.py` - User 模型定义
- `app/routes/auth.py` - 认证相关路由（待创建）
- `app/templates/` - 模板目录
```

## Secretary：秘书角色

### 角色定义：秘书

Secretary 的角色是**秘书**——

> 你是一位经验丰富的秘书。你的工作是接待用户，理解他们的真实需求，自己能处理的就处理，需要专人执行的就安排执行，然后汇报结果。

_（内部视角：Secretary 将结构化的任务规格投递到队列，由 Executor 实例消费执行）_

**秘书隐喻的完整对应**：

| 秘书职责             | Agent 对应             |
| -------------------- | ---------------------- |
| 接待来访、理解需求   | 理解用户意图、多轮澄清 |
| 自己能处理的就处理   | 直接回答简单问题       |
| 需要专业人员就安排   | 委托任务给 Executor    |
| 安排日程、管理优先级 | 任务调度、队列管理     |
| 汇报进展、传达结果   | 呈现执行结果、处理追问 |
| 过滤打扰、保护时间   | 过滤噪音、判断紧急度   |
| 持续可用、长期陪伴   | always on call         |

**核心特质**：

- **亲和力**：让用户感到被倾听和理解
- **洞察力**：能从模糊表述中捕捉真实意图
- **专业性**：知道什么信息是必要的，什么可以推断
- **效率感**：不啰嗦，但也不遗漏关键信息
- **判断力**：知道何时信息足够，何时需要追问

### 职责描述

```markdown
## 你的职责

1. **接待与理解**
   - 友好地接待用户
   - 倾听用户的需求，包括模糊的、不完整的表述
   - 识别用户真正想要解决的问题（可能与字面表述不同）

2. **信息收集与澄清**
   - 判断当前信息是否足以让后台专家开始工作
   - 如果不足，用自然的对话方式引导用户补充
   - 避免像填表一样逐项询问，而是通过对话自然获取

3. **任务结构化**
   - 将用户的需求整理成清晰的任务规格
   - 向用户确认你的理解是否正确
   - 获得确认后，将任务提交给后台专家

4. **结果传达**
   - 收到后台专家的执行报告后，用用户能理解的方式呈现
   - 处理后续追问或新需求

5. **闲聊与关系维护**
   - 适当回应寒暄和感谢
   - 但也要适时引导回正题
```

### 判断逻辑（指导原则而非硬规则）

Secretary 需要自主判断，以下是指导原则：

**何时可以提交任务：**

- 用户的目标清晰（知道要做什么）
- 关键约束明确（知道边界在哪）
- 成功标准可判断（知道怎么算完成）
- 不确定的细节可以合理默认

**何时需要澄清：**

- 存在歧义可能导致完全不同的执行方向
- 缺少的信息无法通过合理假设补全
- 用户可能有隐含的偏好或约束

**何时可以假设：**

- 行业惯例或常见做法
- 用户历史偏好（如果有记忆）
- 可以在执行时验证的细节

### 对话风格示例

**不好的对话**（像填表）：

```text
用户：帮我写个脚本
Agent：请问您需要什么编程语言？
用户：Python
Agent：请问脚本的功能是什么？
用户：处理 CSV 文件
Agent：请问输入文件的路径是什么？
Agent：请问输出格式是什么？
...
```

**好的对话**（像聊天）：

```text
用户：帮我写个脚本
Agent：好的，能简单说说你想让脚本做什么吗？
用户：处理 CSV 文件，把里面的数据汇总一下
Agent：明白了。你是想对 CSV 中的某些列做统计汇总（比如求和、平均值），
       还是想按某个字段分组聚合？另外，CSV 文件大概在哪个目录？
用户：按日期分组，统计每天的销售额。文件在 data/ 目录下
Agent：了解。我确认一下：读取 data/ 目录下的 CSV 文件，按日期分组
       统计销售额，结果输出到新文件。对吗？
用户：对的
Agent：好的，我来处理。
       [执行中...]
       完成了！脚本已保存到 scripts/daily_sales.py，运行后会生成
       daily_summary.csv。要我解释一下代码逻辑吗？
```

### 用户视角的一致性

**关键原则：内部架构对用户透明**

虽然内部是 Secretary + Executor 两个 Agent，但对用户来说：

- 始终面对**同一个助手**
- 不应感知到"前台""后台"的存在
- 不应听到"让后台处理""提交给专家"等措辞

**用户看到的**：

```text
用户 ←→ 统一的 Agent 助手
```

**实际发生的**：

```text
用户 ←→ Secretary ←→ Executor(s)
```

Secretary 负责维护这种一致性幻觉，它是用户看到的"那个助手"的全部面孔。

### 与 Executor 的异步协作

Secretary 与 Executor 通过**消息队列**异步通信，而非同步调用：

```text
┌─────────────────┐                        ┌─────────────────┐
│   Secretary     │                        │   Executor (N)  │
│   (分诊经理)    │                        │   (技术专家)    │
│                 │                        │                 │
│   理解用户      │    Task Queue          │   规划执行      │
│   澄清意图      │  ═══════════════════▶  │   调用工具      │
│   管理任务      │    (异步投递)          │   验证结果      │
│   呈现结果      │                        │   报告状态      │
│                 │    Report Queue        │                 │
│   [always on]   │  ◀═══════════════════  │   [可多实例]    │
└─────────────────┘    (异步回传)          └─────────────────┘
```

**通信协议**：

- Secretary → Task Queue → Executor：Task Specification
- Executor → Report Queue → Secretary：Execution Report

**异步带来的变化**：

- Secretary 投递任务后立即返回，继续与用户对话
- Executor 完成后将报告放入队列，Secretary 择机通知用户
- 多个 Executor 可并行消费任务

## 处理非任务型请求

### 请求的两个维度

请求的处理方式取决于**两个维度**：

```text
                        工作量/深度
                            ▲
                            │
           需要调研         │         需要执行
        (Executor 调研)     │      (Executor 执行)
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
        │  "分析整个项目    │  "重构这个模块"   │
        │   的架构问题"     │                   │
        │                   │                   │
        │  "找出所有性能    │  "修复这 10 个    │
        │   瓶颈"           │   性能问题"       │
        │                   │                   │
────────┼───────────────────┼───────────────────┼────▶ 是否有副作用
        │                   │                   │
        │  "这个函数是      │  "把这个函数      │
        │   做什么的？"     │   改成异步"       │
        │                   │                   │
        │  "A 和 B 哪个     │  "帮我安装 A"     │
        │   更合适？"       │                   │
        │                   │                   │
        └───────────────────┴───────────────────┘
           直接回应              同步执行
        (Secretary 处理)      (Executor 同步)
```

**关键洞察**：分析型、探索型问题在浅层时可以直接回应，但深入后就变成了**调研任务**——虽然没有副作用，但需要大量的阅读、搜索、分析工作。

### 任务的三种形态

| 形态         | 特征                           | 示例                       | 处理方式            |
| ------------ | ------------------------------ | -------------------------- | ------------------- |
| **对话回应** | 基于已有上下文，即时回答       | "这个函数的作用是什么？"   | Secretary 直接回应  |
| **调研任务** | 需要深入调查，但无副作用       | "分析项目中所有的性能瓶颈" | Executor 调研后报告 |
| **执行任务** | 需要修改文件、运行命令等副作用 | "修复这些性能问题"         | Executor 执行       |

### 调研任务的识别

何时将分析型请求升级为调研任务：

| 信号                   | 示例                                 |
| ---------------------- | ------------------------------------ |
| **范围广泛**           | "整个项目""所有模块""全面分析"       |
| **需要多文件交叉分析** | "找出所有调用这个接口的地方"         |
| **需要运行/测试验证**  | "哪些测试覆盖了这个功能"             |
| **信息不在当前上下文** | "去年那个 PR 的改动逻辑是什么"       |
| **需要外部资源**       | "这个库的最佳实践是什么"             |
| **用户明确要求深入**   | "仔细分析一下""深入调查""彻底搞清楚" |

### 调研任务的 Task Specification

调研任务同样使用 Task Specification，但目标是**产出分析报告**而非代码变更：

```markdown
---
task_id: task-20260123-003
created_at: 2026-01-23T14:00:00Z
type: research # 标记为调研类型
---

# 调研任务：分析项目中的性能瓶颈

## 调研目标

找出项目中可能的性能瓶颈，按严重程度排序，并给出改进建议。

## 调研范围

- `src/` 目录下的所有 Python 代码
- 重点关注数据库查询和循环处理

## 期望产出

1. 性能问题清单（按严重程度排序）
2. 每个问题的位置、原因分析、建议方案
3. 优先处理建议

## 调研方法建议

- 静态分析：查找 N+1 查询、大循环、同步阻塞
- 如有性能日志/监控数据，优先参考
```

### Secretary 的角色演变

Secretary 的角色不是"能直接回答就回答"，而是**判断请求需要什么级别的处理**。

详见下文"请求分类的判断逻辑"。

### Secretary 的降级机制

Secretary 的评估可能过于乐观，这是可以接受的。关键是要有**降级能力**：

```text
用户请求
    │
    ▼
┌──────────────────────────────────────────────────┐
│                  Secretary                       │
│                                                  │
│   评估：可以直接回应                             │
│          │                                       │
│          ▼                                       │
│   尝试回应 ─────────────────┐                    │
│          │                  │                    │
│          ▼                  ▼                    │
│       成功？             失败/不足               │
│          │                  │                    │
│          ▼                  ▼                    │
│      返回用户         降级委托 Executor          │
└──────────────────────────────────────────────────┘
```

**降级的触发条件**：

| 情况             | 示例                               |
| ---------------- | ---------------------------------- |
| **信息不足**     | 尝试回答但发现需要读取更多文件     |
| **复杂度超预期** | 问题比预想的更复杂，需要深入分析   |
| **置信度不足**   | 能给出答案但不确定准确性，需要验证 |
| **需要工具支持** | 回答需要运行代码、搜索等工具辅助   |

**降级时的行为**：

```text
用户：这个模块的依赖关系是怎样的？
Agent：[尝试基于上下文回答]
       让我看一下... 这个模块依赖于 A 和 B...
       [发现信息不足，需要分析更多文件]

       这个问题比较复杂，我需要仔细分析一下整个依赖图。
       稍等，我来做一个完整的分析...
       [委托 Executor 进行调研]
```

**关键原则**：

- 乐观评估是允许的（避免过度保守导致简单问题也要等待）
- 但必须能识别失败并快速降级
- 降级对用户应该是自然的（"让我仔细看看"），而非暴露内部机制

### 对话示例：从快速回答到深入调研

```text
用户：这个项目的架构是怎样的？
Agent：从目录结构看，这是一个典型的分层架构：
       - `api/` 处理 HTTP 请求
       - `service/` 业务逻辑
       - `repository/` 数据访问
       使用了 FastAPI + SQLAlchemy 技术栈。

用户：有什么架构问题吗？
Agent：初步看有几个常见风险点：
       - service 层有些直接访问了数据库，跳过了 repository
       - 看到了一些循环导入的迹象
       要我深入分析一下吗？这需要我仔细检查整个代码库。

用户：好的，帮我仔细分析
Agent：明白。我会全面分析代码库的架构问题，包括：
       - 层次违规（跨层调用）
       - 循环依赖
       - 模块耦合度
       - 接口设计问题

       这需要一些时间，分析完成后我会给你一份详细报告。
       [提交调研任务到 Executor...]
```

### Secretary 的双重角色

Secretary 不只是"任务提交器"，它同时是一个**有能力的对话者**：

```text
用户请求
    │
    ▼
┌──────────────────────────────────────────────────────┐
│                  Secretary                           │
│                                                      │
│   ┌─────────────┐         ┌──────────────────────┐   │
│   │ 请求分类器  │ ──────▶ │ 需要 Executor？      │   │
│   └─────────────┘         │                      │   │
│                           │ YES → 提交 Executor  │   │
│                           │ NO  → 直接回应       │   │
│                           │ 不确定 → 尝试后决定  │   │
│                           └──────────────────────┘   │
└──────────────────────────────────────────────────────┘
```

**Secretary 可直接处理的请求**（浅层/中层）：

- 分析类问题（基于当前上下文的评估、审查）
- 咨询讨论（比较、建议、权衡）
- 解释类问题（说明、教学、概念澄清）
- 探索类对话（头脑风暴、可能性探索）
- 社交性对话（寒暄、感谢、闲聊）

**需要提交 Executor 的请求**：

- 执行类：需要修改文件、运行命令等**副作用**（无论深浅）
- 调研类：需要大量阅读/搜索/分析的**深层**分析、咨询问题
- 长时间任务：预计需要较长时间完成的工作

**边界情况（尝试后决定）**：

- 中层分析/咨询类：Secretary 先尝试，超出能力则降级

### 请求分类的判断逻辑

```markdown
## 分类决策树

1. **是否需要副作用（文件修改/命令执行）？**
   - 是 → 提交 Executor（浅层同步，深层异步）
   - 否 → 继续判断

2. **是否明显需要大量调研工作？**
   - 是（范围广、多文件、需外部资源）→ 提交为调研任务
   - 否 → 继续判断

3. **能否基于当前上下文回答？**
   - 能 → Secretary 直接回应
   - 不确定 → Secretary 尝试，失败则降级
```

> **与降级机制的关系**：步骤 3 中的"不确定"情况会触发降级机制。
> Secretary 乐观尝试，发现信息不足或复杂度超预期时，委托 Executor。

**判断"快速回答"的标准**：

- 信息已在对话上下文中
- 是常见知识或模式
- 不需要精确验证（"大致是这样"可接受）

**判断"需要调研"的标准**：

- 需要阅读多个文件
- 需要搜索/追踪代码
- 需要交叉验证信息
- 用户期望准确、全面的答案

### 开放性问题的处理策略

对于没有明确成功标准的开放性问题：

| 问题类型       | 处理策略                             | 示例                                                       |
| -------------- | ------------------------------------ | ---------------------------------------------------------- |
| **分析型问题** | 给出结构化分析，列出多个角度         | "这个架构有什么问题？"→ 列出 3-5 个潜在问题点              |
| **比较型问题** | 给出对比表格，说明各自优劣和适用场景 | "Redis vs Memcached？"→ 对比表格 + 推荐场景                |
| **探索型问题** | 提供选项，引导用户明确方向           | "要不要重构？"→ "重构可以带来X，但成本是Y，你更关注哪个？" |
| **验证型问题** | 给出诚实评估，包含确定和不确定的部分 | "我的方案可行吗？"→ "可行，但需注意A和B"                   |
| **创意型问题** | 提供多个可能性，不急于收敛           | "有什么好的实现方式？"→ 列出 3 种方案各有特色              |

### 成功标准模糊时的应对

**核心原则：不要假装成功标准明确**

当成功标准本身模糊时：

1. **承认模糊性**："这个问题没有标准答案，取决于..."
2. **给出框架**："可以从这几个维度考虑..."
3. **提供选项**："常见的做法有 A、B、C，各有利弊"
4. **邀请共创**："你倾向于哪个方向？我们可以深入讨论"

**对话示例**：

```text
用户：帮我 review 一下这个代码
Agent：好的，我来看看。

       从可读性角度：
       - 函数命名清晰 ✓
       - 有些地方缺少注释，特别是第 42 行的算法逻辑

       从性能角度：
       - 第 78 行有 N+1 查询问题
       - 整体可接受，除非数据量很大

       从可维护性角度：
       - 建议把 utils.py 里的那个长函数拆分

       你希望我深入哪个方面？或者有其他关注点？
```

### "非任务"请求的价值

这些看似不是"任务"的请求，其实有重要价值：

1. **建立理解**：帮助用户（和 Agent）建立对问题的共同理解
2. **探索空间**：在明确任务前探索可能性空间
3. **降低风险**：避免在错误方向上投入执行
4. **增强信任**：展示 Agent 的判断力和专业性

### 从对话到任务的渐进转化

很多时候，对话会自然演化为任务：

```text
用户：我在想要不要重构这个模块                     [思考陪伴]
Agent：重构可以提升可维护性，但需要时间。
       你主要想解决什么问题？
用户：主要是太难测试了                             [探索]
Agent：确实，我看到有几个大函数，依赖也比较紧密。
       可以考虑：1)拆分函数 2)依赖注入 3)接口抽象
用户：依赖注入听起来不错，能帮我做吗？             [明确任务]
Agent：好的。我先分析一下依赖关系，然后给你一个
       重构方案确认。确认后我开始执行。
```

Secretary 需要识别这种**渐进转化**，而不是一开始就强求用户给出明确任务。

## 优势分析

### 1. 关注点分离

| 方面     | Secretary                    | Executor                |
| -------- | ---------------------------- | ----------------------- |
| 核心能力 | 语言理解、对话管理、任务调度 | 任务规划、工具使用      |
| 输入     | 模糊的自然语言               | 结构化规格              |
| 输出     | 澄清问题、确认理解、进度通知 | 执行结果、状态报告      |
| 上下文   | 对话历史 + 任务列表          | 单一任务规格 + 执行状态 |
| 生命周期 | 长期运行（用户会话）         | 短期运行（单任务）      |

### 2. 上下文隔离

- Executor 的上下文**不包含对话噪音**，只有干净的任务规格
- 避免了 "越走越累的长跑者" 问题
- 每次执行都从干净状态开始
- 每个 Executor 实例处理单一任务，互不干扰

### 3. 可用性与弹性

- Secretary always on call，用户永远不会等待
- Executor 可水平扩展，根据负载动态增减
- 单个 Executor 失败可重试或转移到其他实例

### 4. 可测试性

- Secretary 可以独立测试意图理解能力
- Executor 可以独立测试执行能力
- 接口契约（Task Specification）便于测试和验证

### 5. 灵活性

- 可以为不同类型任务使用不同的 Executor
- Secretary 可以根据用户习惯调整对话风格
- 可以在任务提交前插入人工审核环节
