## 12. 实现记录：Explorer / GitLens 的 stack sash 拖不动（2026-10-26）

**现象**：Explorer 里上下拖「OPEN EDITORS / 文件树」之间的 sash，行高不变；GitLens 的 stack 同样。区域边界（左/中、上/下）正常。

**根因（证据）**：`PRAC_SHELL_CSS`（`packages/bundle/web-app/src/client/title-bar.tsx`）里

```css
[data-prac-region^="left/"]{flex:1 1 auto!important;min-width:0!important}
```

本意是让左栏的活动容器填满，但它用**前缀匹配**，同时命中 stack 的行区域（`left/container:…/stack/<view>`），且带 `!important`，覆盖了行上的内联 `flex: 0 0 <allocated>px`。浏览器实测：行的 `style` 是 `flex: 0 0 120px`，computed 却是 `flex: 1 1 auto`；行高由 flex 比例决定（462.16 / 368.17 / 87.67 这类小数）。所以 `startEntryDrag` → `setEntryHeight`（写 `size`、`flex:false`）和 `resolveSizes`/`allocateStack` 都在正常工作，只是被这层 CSS 挡住——拖动「看起来活着、DOM 不动」。

**修复**：把选择器收窄为 `[data-prac-region^="left/"]:not([data-prac-stack-row])`。行不再是规则目标，computed flex 与内联一致（120/288/288），拖动开始改变 DOM 与持久化 `size`。

**同一次修复里暴露/修掉的两处几何不一致**（此前被上面那条 flex 规则掩盖）：

1. `frame.ts` 的 viewport 用 `getBoundingClientRect()`（border box），而 shell 给 frame 加了 `padding-top:38px`（固定标题栏的占位）。`resolveSizes` 的根 split 实际画在 content box 里，于是分配比可见区大 38px。改为测量 content box（减去 computed padding）。
2. shell 用 CSS `display:none` 隐藏 bottom 轨道，但视图还在，`isPresent` 判 true，分配仍给 `bottom` 240px——侧栏底部因此空出 240px。改为在 arrangement 里把落在 `bottom`/`bottom/…` 的视图 **hide**（`placeCatalogue` 与 `arrange` 都收口到 `hideOffScreen`）；隐藏视图走模型自己的 presence 规则，轨道从分配里消失，视图仍可被 recall 找回。补了单元测试（`arrangement.spec.ts` 新增 2 条 + 修正 4 条与现状漂移的旧断言）。

**验证（真实 3084，Playwright）**：

- Explorer：拖 `left/container:workbench.view.explorer:3` 下移 60px → `OPEN EDITORS 120 → 180`、`fileView 389 → 329`，其余行不动；持久化 `size` 同步（120→180 / 389→329）。
- GitLens：从 activity 切到 GitLens，拖第一条 stack sash 下移 50px → `graph 188 → 239`、`welcome 188 → 138`，其余行不动；持久化同步。
- 区域边界 `top:1` 右拖 40px → `left` 宽 `280 → 320`，未回归。
- 修复后 stack 行合计 = 942（split 962 − 20px 被隐藏的 container bar），视觉上侧栏已填到底。

**残留**：那 20px 来自机制按「有多个 child 就画 20px container bar」预留高度，而 shell 用 CSS 隐藏了 bar。要么给 RegionNode 加一个「不画 bar」的显式状态（机制改动，需裁），要么让 bar 显示/改成 overlay；当前先记录，未动机制。

**回归面**：`tests/gates/verify-stack.mjs` 本来就在拖 sash 后比较**绘制高度**，能覆盖这条路径；这次的问题是 shell CSS 覆盖，单测无法覆盖，live gate 才是正确层级。

## 13. Dock 决策 + P0：selector 形态进模型（2026-10-26）

**2026-10-26 的裁决**（James）：采用 dock 模型；默认 agent 在右；rail 常显；chat 最大化占 editor area，但右 dock / rail 仍可用。设计收进 [2026-10-23-ui-scheme.md](../notes/in-progress/2026-10-23-ui-scheme.md) 的 Decisions / 布局 / 行为 / 验收。

**P0（本次落地的机制切片）**：`RegionNode.selector: "rail" | "title" | "none"`。

- `drawsRegionBar(node)` 统一「画不画 in-region 选择器」；`resolveSizes` 只在 `title`（或旧默认）时减 `HEADER_HEIGHT`。`rail` 的 rail 在 region 外，`none` 不画，二者都不再预留 20px。
- 左 region 在 `arrange` 里声明 `selector: "rail"`，bottom `"none"`；frame 因此不再渲染 `[data-prac-container-bar="left"]`（不是 CSS 隐藏）。
- 新增 face 方法 `selectContainer(regionId, childId)`（rail 的点击不再 `.click()` 隐藏按钮）和 `activeContainer(regionId)`（rail 的高亮问 frame，而不是猜 view 的 region）。
- 证据（全新 3084）：`left` selector 持久化为 `rail`；没有 container-bar 元素；Explorer stack 行合计 **962**（split 962，之前的 20px 缺口消失）；rail 切 GitLens / 回 Explorer 正常且高亮正确；拖 `…explorer:3` 下移 60px → `120/399 → 180/339`，合计仍 962。
- 测试：`selector.spec.ts` 6 条（rail/title/none、单 child、幂等）；ui-layout 205 条、web-app 26 条全过；两个包 `vp check` 过。

**未做（P1）**：右 dock 的 rail（常显）、chat 最大化/回右 dock 的布局、右 dock 其它工具窗口。需要先决定「最大化 = placement 还是 home+promotion」；当前 UI 仍沿用原来的 center/right 放置逻辑。

## 14. P1：右 dock + chat 最大化（2026-10-26）

**实现的模型**：右 dock 是一块内容 region + 一条常显的 rail；rail 在 frame 的 `padding-right` 里（1600: 48px，768: 44px），dock 内容可以没有（只留 rail），rail 不消失。左/右 region 都声明 `selector: "rail"`。chat 的默认位置是右 dock；无文件时 `restoreCentre` 把它放到 editor area（最大化），打开文件 `openFileInto` 把它放回右 dock。

**改动**：

- `title-bar.tsx`：`PracActivity`/`PracActivityFace` 泛化为 `PracRail`/`PracRailFace`（items / onDidChange / select）；`PracRailItem.maximized` 用一个小圆点表示「在 editor area，不在本 dock」；右 rail 的 CSS（贴右边、active 指示翻到右侧）、`[data-prac-frame]{padding-right:48px}`、768 的 44px 与 drawer `right:44px`。
- `index.ts`：两份 rail face。左侧 = catalogue 的 sidebar containers（保留空的 Run and Debug），active 用 `activeContainer(LEFT)`；右侧 = chat + `regionChildren(RIGHT)` 的工具窗口（用 region children 而不是 catalogue，Copilot Chat 未 placed 就不会出现）。两者都订阅 layout + catalogue；rail 点击走 `selectContainer`（右 dock 还会 `setCollapsed(RIGHT,false)`）。
- `arrangement.ts`：`right` 也 `setRegionSelector(RIGHT, "rail")`。
- `frame.ts`（修 P1 暴露的 bug）：`top:2`（editor/右 dock）的 sash 原本测 `previousElementSibling` 的 rect；`stage` 是单格 grid，`display: contents`，rect 是 0，于是 sash 被放到 `left: -2px`。改为当 previous 的 rect 为空时回退到分配 `offset`。

**证据（真实 3084，全新上下文）**：

- 1600 无文件：右 rail `x=1552,w=48`，Chat 项 `maximized`；左 rail 5 项（Explorer/Search/SCM/Run/GitLens）；chat region `center`；右 dock 不渲染；frame `padding-right:48px`。
- 打开 `build_resume.py`（Quick Open）：chat region `right`，右 dock `x=1132,w=420`，editor `x=280,w=852`；右 rail Chat `active`。
- 关闭编辑器（workbench 的 `Close Editor (⌘W)` action）：chat region `center`，文件 0；右 rail Chat `maximized`。
- `top:2` 位置修复：`left: 1130px`（= 1132 − half），拖动 −100px → right 420→520，center 852→777（3-child 的 distribute 语义会同时按比例分给左侧，这是既有设计，见 `resize-regions.spec`「distributes over the whole side」）。
- 768：右 rail `x=724,w=44`；右 dock 以 drawer 形式 `x=323,w=401`（`right:44`，不压 rail）；左 rail 44。
- ui-layout 205 条、web-app 26 条测试过；两包 `vp check` 过。


**P1 补：Layout 菜单（移动工具窗口 / 收起右 dock）**

- 标题栏新增 `▦` Layout 菜单（`PracTitleFace.layoutActions()`；菜单在建时问一次，进程内由 catalogue inject 填）。
- `moveContainer(containerId, "left"|"right")`：把容器的视图 `place` 到目标 dock 的 `container:<id>` 子 region，再从源 region 的 children 里移除；目标 dock 若只有 chat 直挂，先给 chat 建一个 child，避免新 child 把直挂的 chat 遮住；移动后右侧 rail 用 `regionChildren(RIGHT)` 列出它，左侧 rail 用 `listViews()` 排除已在右 dock 的容器（Run and Debug 这种没有 placed view 的容器仍保留）。
- `collapsedOf` + `setCollapsed(RIGHT, …)`：Layout → Hide/Show right dock；rail 在 frame padding 里，所以收起后 rail 仍在。左 dock 没有做，因为它的 rail 现在在 left region 的 padding 内，收起 left region 会让 rail 压在 editor 上。
- 证据：无文件 → Move GitLens to right dock：chat 仍 center（rail dot），right region 420 + GitLens，右 rail `chat`(max) + `right/container:…gitlens`(active)，左 rail 剩 4 项；Hide right dock：right `collapsed=true`、宽 0、rail `x=1552` 仍有两项；点 GitLens rail → right 恢复 420；Move GitLens to left dock：右 region 空、左 rail 5 项、GitLens active。

**P1 未做**：agent-left preset；左 dock 的收起（需要把左 rail 也挪到 frame padding 外，才能不压 editor）。右 dock 默认只有 chat；Layout 菜单可以把左侧容器移过去。
- 边界（文件打开、chat 直挂右 dock）：Move Explorer to right dock 时先给 chat 建 child、再移动 Explorer；right children `["right/dsh:main:conversation","right/container:…explorer"]`，右 rail Chat 非 active + Explorer active；点 Chat → Chat child 被选中（active），Explorer 变非 active；Move Explorer back → right 只剩 chat child，左 rail Explorer active，右 rail Chat active。

- 前提：当前实现基于 workspace/project；必须先有 workspace/project，文件、notes、git、session、agent、desktop 才能工作。note 的第一节改为 Workspace/project first；first-run 是 workspace 选择；所有 app/desktop/session/agent 都是 workspace 作用域。

- note 重写为 OS-like desktop：apps / docks / panels / stage / tiles / focus / virtual desktops / agent backend / human freedom；之前的 B（固定 editor 896 + 右 sidebar 388）降为「chat 收进 panel」的一种 desktop。
- 代码仍 pre-OS；下一步实现分阶段：app/panel/dock → stage tiles/focus → virtual desktops → agent backend/review；workspace/project 基座已存在，不回退。

- 复现：先开 `.txt` 再开 `.md`，或 fresh page 直接开 `.md`；`.monaco-breadcrumbs` 的 DOM 有 5 个 item、容器 1200px，但 widget 的 inline width 是 **0px**，所以画面上看不到路径。第二次打开同一个 md 就正常（1117px）。

- 修：`PracEditorGroup.openEditor` 在同步 `relayout()` 后再排一个 `setTimeout(..., 0)` 的 `relayout()`（disposed 时跳过）。一帧后 picker 的真实宽度已成立，widget 拿到剩余宽度。
- 验证：md first 和 txt→md 两种顺序都得到 `width: 1117px`、5 个 item 可见；截图 [breadcrumbs-markdown.png](assets/2026-10-23-ui-scheme/breadcrumbs-markdown.png)，脚本 [verify-breadcrumbs.mjs](assets/2026-10-23-ui-scheme/verify-breadcrumbs.mjs)。`prac-vscode` 全量重建通过；`pnpm check` 仍只剩 overlay 既有格式问题。

## 51. Markdown LSP / Outline / in-file breadcrumbs（2026-10-28）

- 现象：markdown 的面包屑只有文件路径，没有文件内 heading 层级；Outline 空。
- 事实：TypeScript 的 Outline 正常（Alpha / value / Beta / method），说明 extension host 与 LSP 通路是好的。Markdown 的扩展 host 报 `Activating extension 'vscode.markdown-language-features' failed: Cannot find module …/markdown-language-features/out/extension`——`markdown-language-features` 没在 `BUILTIN_EXTENSIONS` 里编译，扩展扫到了但激活不了，所以没有 markdown language server。

## 52. 多个 markdown tab 切换时面包屑宽度偶发归零（2026-10-28）

- 复现：同一个 group 里开两个 `.md`，快速点 tab（每次间隔 250ms 读一次）。10 次里会有一次 `.monaco-breadcrumbs` 的 inline width 变成 `0px`，但 item 文本（路径 + heading）都在，所以看起来就是“面包屑没了”。慢速切换通常正常，因此容易误判成偶发。
- 根因：还是 header 的懒加载 editor type picker / breadcrumbs 布局竞态；之前只在 `PracEditorGroup.openEditor` 末尾补一次 `setTimeout(relayout)`，而 **tab 切换走的是 active editor change，不是 app 的 openEditor**，所以这条路径没有第二次 layout，撞上 mid-flight 宽度就停在 0。
- 修：`PracEditorGroup` 订阅 `onDidActiveEditorChange`，统一调用 `scheduleRelayout()`；`openEditor` 末尾也复用同一个 helper。即每次 active editor 变化后一个 task 再 layout 一次。
- 验证：3 轮 × 10 次快速 tab 切换，全部 1117px（修复前 30 次里会出现 0）；慢速同 group 切换、两个 editor group 各自切 tab 也都正常。截图 [markdown-tab-switch.png](assets/2026-10-23-ui-scheme/markdown-tab-switch.png)，脚本 [verify-md-race.mjs](assets/2026-10-23-ui-scheme/verify-md-race.mjs)。

## 53. 面包屑归零的真正根因：editor type picker 被量成整条 strip（2026-10-28）

- §52 的“active editor change 后再 relayout”只是补了一次 layout，仍能复现：普通速度点 tab、每次 2s，两三个来回后 `.monaco-breadcrumbs` 仍是 `width: 0px`。
- 插桩 `BreadcrumbsControl.layout` 后看到最终一次输入是 `inWidth: 1215, typeWidth: 1215, outWidth: 0`：`EditorHeaderControl` 把 header 可用宽度交给 `BreadcrumbsControl`，后者减掉 `_editorTypeNode.offsetWidth`；在 tab 切换的某个瞬间，picker 还没拿到 flex sizing，`offsetWidth` 等于整条 header（1215px），减完就是 0。下一次 layout 能变成 `typeWidth: 83, outWidth: 1117`，但失败时最后一次 layout 恰好是那个瞬态，之后没有新的正值 layout。
- 修：`PracEditorGroup.layout` 在 header layout 前把 `.breadcrumbs-editor-type` 的 inline sizing 钉住：`width: max-content; max-width: 40%`（40% 与上游 CSS 一致）。这样 `offsetWidth` 不再可能量成整条 strip，面包屑最坏也只是宽度略窄，不会是 0。
- 另外保留两个防御：`layout` 不把瞬态 `0×0` 写进 `_dimension`（保留上一个真实尺寸）；active editor change 后一个 task 再 relayout。
- 验证：真实 notes 两个 md、普通 2s 切换，连续 5 轮 × 12 次无 0（修复前 3 轮里 2 轮出现）；截图 [markdown-tab-switch.png](assets/2026-10-23-ui-scheme/markdown-tab-switch.png)，脚本 [verify-md-switch.mjs](assets/2026-10-23-ui-scheme/verify-md-switch.mjs)。

## 54. 换成上游 patch：不靠改 picker inline style（2026-10-28）

- 审 §53：那不是干净解法——`PracEditorGroup.layout` 每帧去改上游 picker 的 inline `width/max-width`，是在 sympton 上钉尺寸；再叠加 active change 重排，都是时序补偿，上游改结构就失效。
- 干净一点的做法：把判断放回 `BreadcrumbsControl.layout` 的源头。新增 `vendor/vscode/patches/0003-breadcrumbs-picker-width.patch`：当 picker 的 `offsetWidth` 不小于可用宽度时，不把它当成下拉的真实宽度（那是 flex sizing 尚未生效的整条 strip）；上游已有的 `_updateEditorTypeControl` 会在 picker 真实宽度变化后重跑 layout。picker 保留，不再需要每帧改 DOM。
- 同时删掉 §52/§53 的 active-change 重排与 inline picker 尺寸；`PracEditorGroup` 只留一个防御：region 在 re-parent 的瞬间报 `0×0` 时，不把这个瞬态写进 `_dimension`（保留上一个真实尺寸）。这是 view host 生命周期上的真实约束，不是面包屑特判。
- 验证：真实 notes 两个 md、普通 2s 切换，连续 10 轮 × 12 次无 `width: 0`；截图 [markdown-tab-switch.png](assets/2026-10-23-ui-scheme/markdown-tab-switch.png)，脚本 [verify-md-switch.mjs](assets/2026-10-23-ui-scheme/verify-md-switch.mjs)。
- 代价：多一个 vendor patch，升级 VS Code pin 时要跟着 rebase；这是把补丁放在正确边界（上游测量）换来的，不是零成本。若不想维护 patch，另一条干净路线是 prac 不显示 editor type picker（产品取舍），但会失去切换 editor type 的入口。

## 55. 桥接确实改掉了上游 editor 的 DOM/CSS 上下文（2026-10-28）

- 查 `PracEditorGroup` 的实际祖先链：`.editor-group-container.prac-editor-group` **直接挂在 `.monaco-workbench` 下**，没有 `.part.editor > .content`；标题是 `.prac-editor-title`，不是上游的 `.title`。
- 上游 editor 的 CSS 大量作用域是 `.monaco-workbench .part.editor > .content .editor-group-container > .title …`（`editorgroupview.css` / `editortitlecontrol.css` / `breadcrumbscontrol.css`）。这些规则在我们这里根本不匹配；prac 是用自绘 title/手工 width/height 补出来的。只有少数全局规则（如 `.breadcrumbs-control.with-editor-type` 的 flex）会命中，于是 picker/面包屑的尺寸语义就和上游不一致。
- 试过最小 DOM 对齐：给 group 外面套 `display:contents` 的 `.part.editor > .content`，并给 title 加 `.title`。面包屑宽度从 1117 变成 1215，说明上游规则确实开始命中，但也说明**只补祖先不够**：title/actions/tabs 的组成仍是 prac 自绘的，width 账算不平，不能直接上线。已回退这个实验。
- 结论：这不是“上游有 bug”那么简单，**桥接替换了整个 editor part，却只保留了 group 的内部类名**。干净的修法是把 `PracEditorGroup` 的 title/actions 组成也对齐上游（或明确写出一层 prac 的 title CSS contract），然后删掉 0003 patch；只补 `.part.editor` 外壳是半成品。

## 57. 按 window 模型重裁 editor host 的 note（2026-10-28）

## 58. container = window，container window 也能进 stage（2026-10-28）

- 纠正模型：window 是从 container 演化来的内容容器；view 在 window 内（stack）。Explorer / SCM / GitLens 本身是 window，Folders / Changes / Outline 是它内部的 view。
- placement（dock / panel / stage）和 content kind（editor / container）分开：container window 也可以进入 stage，成为 window group 的 tab；此时它是 editor input / EditorWindow，pane 内容是一个 view stack。
- `ui-vscode-views` 因此不是“每个 view 一个 prac.view”，而是提供 container window + 内部 views；`ui-vscode-editor` 提供 editor window；两者共享 `vscode-host` 的 window/view host 契约。

## 59. Window 级隔离；EditorWindow 直接托管 EditorPane（2026-10-28）

- 接受“托管 EditorPane 更简单”：EditorWindow 是薄宿主，不引入额外 VscodeHost 层；拿到 frame 给的 window 内容根后直接挂 `EditorPane` / container 的 view stack。
- 隔离单位从“每个 view”改为“每个 window”：frame 给 window 一个 shadow root / 内容根；window 内的 views、editor pane 共享；webview / iframe / opaque view 才在自己的 host 内再隔离。window 是 containment / stacking / theme / focus 的边界；tab strip / actions 在 window 外。
- 交叉 window 的 overlay 走 frame float layer；pane 自己 DOM 内的 overlay 留在 window 内。

## 60. Window 隔离与 VS Code / DSH 混排（2026-10-28）

- 结论：window 是外层 containment / stacking / theme / focus 边界，但不能把混排 window 内的 views 直接合并成一个 shadow root。
- 具体冲突：frame 的 pane header 用 `:host` / `:host-context`（per-view root 才成立）；VS Code 的 CSS 依赖 `.monaco-workbench` 语境和 per-view `contain: paint`；DSH 的 CSS 按自己的 root / CSS modules 作用域。共享 root 会让两边的全局/reset/变量/overlay 互相穿透，`frame.ts` 的 `:host` 选择器也会指向 window 而不是 view。
- 策略：window 外层隔离 + 混排 window 保留 per-view root / source-scoped 子树；同源 window 才考虑合并。webview / iframe / opaque view 始终自己的 browsing context / host。
- 需要改的：`ui-layout` 的 `isolation.ts` 从“per view host”改为“window host + 可选 per-view child root”；`frame.ts` 的 `:host` / `:host-context` 规则要么保留 per-view root，要么迁移到 view wrapper 的 class/data 选择器。
- 已同步 10-05 / 10-07 / 10-20 的相关段落。

## 61. Window 由 app 打开；view 可重组（2026-10-28）

- 修正：window 不是独立注册的实体；application 定义 window kinds / open 动作，window 是 app 打开的实例，带 `appId`。没有“无主 window”。
- VS Code 的 view 本来就可以重组：Timeline 可从 Explorer 拖到 right sidebar 或另一个 container，形成单 view 的 container window。因此 view 是 **placement**，不是固定子节点；移动只改 view → window 的 placement，source / 内容身份不变；一个 window 可以容纳其他 app 的 views。
- 映射仍成立：VS Code editor input → window；view container → container window；view → movable view。区别是 container 不是固定 owner，window 也不是自由实体。
- 已同步 10-07 / 10-20 / 10-23。
- 待定：把一个 view 拖到空处、创建新的单 view container 时，由谁打开这个 window——是 view 的 source app，还是 shell 的通用 container app？这是 app/window 归属的关键决策。

## 62. Widget model 作为设计基线（2026-10-28）

## 65. UI package 重新划分与 bundle 边界（2026-10-28）

## 142. S2 的形态：mapping-only（2026-10-30）

## 144. 权威按事实分：frame 组合 / 来源内容（2026-10-30）

- James 澄清：prac 的状态为权威，VS Code adaptor 只做投影；并问是否扩大到 editor / webview。
- 结论：不是“所有状态都归 frame”，而是**按事实分**：
  - window 存在 / order / active / placement / 几何 / chrome → frame；
  - editor 的 input / buffer / dirty / undo / view state → VS Code editor runtime；
  - webview 的 document / 内部状态 → webview runtime；
  - chat / board 的内容 → frame / DSH；
  - adaptor 是投影 + host，不是内容第二所有者。
- 由此：不要镜像内容状态；投影方向按事实（window order/active 是 frame→model，open/close/activate 是命令→frame）；content host 归来源（EditorPane / webview element / frame 自己渲染）。
