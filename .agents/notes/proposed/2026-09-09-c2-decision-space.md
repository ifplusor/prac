# C2 决策空间 —「带依据的候选决策」成为模型可见输入 & 审决策为主界面

> 这是 C2 的候选决策，处于 `proposed`（在论证，未裁决）。它是一份**决策记录**，不是工作便签：观察/开放问题是它的**输入**，写在他的决策/问题里，不单独成 note（按模型 note 的定义，观察、开放问题属工作表面，待决断/确立为方向后才会凝结为 note）。
> 未证实的成本一律标注「未验证」，不用我的判断冒充事实。

---

## 0. 一条输入约束（来自协作偏好，非独立决策）

- **James 偏好「基于文件/画布的讨论式协作」**。这作为 C2 设计的一条**输入约束**：C2 的「审决策」呈现不该是聊天/填表式追问，而应把决策空间做成**一块可共读、可批注、可逐层展开的文档/画布**。
- 它**不是**一条独立 decision note——目前只是工作偏好的观察 + 一个开放问题（见 §5），待其被决断为 prac 方向后才值得凝结。
- **画布 vs 文件**：眼下可用的是「文件」；「画布」（可视化决策空间板）prac 暂无基建，属 C3+ 方向，此处不作承诺。

---

## 1. 核心问题（已拆解，不是三选一）

要物化一个**带依据的候选决策**为一等公民对象，让它同时满足：

1. **模型可见** —— 模型能读到它、据此继续推理；
2. **可审** —— 你能在 surface 上看到它并裁决；
3. **可持久 / 可重建** —— 满足 DSH 的「model-visible ⟺ logged」，并能归档进架构记忆；
4. **可承载依据** —— 选项、代价、推荐、验证计划。

**DSH 根本约束**：凡到达模型请求的东西都必须能从 session log 重建。所以这不是「工具 vs 上下文注入 vs 交互呈现」三选一，而是：**把这个对象在 session log 里的「真相源」定成什么**，再决定它怎么进模型视野、进你的视野。

---

## 2. 已核实事实 vs 未验证

**已核实（DSH 缝，来自 `docs/capability-seams.md` + 源码 + C1 验证）：**

| 缝                                                             | 角色                         | 状态                                                                                                                |
| -------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `ctx.tools.register`（工具）                                   | 模型**产生**候选决策         | ✅ C1 已验证（`prac_ping`）                                                                                         |
| `ctx.sessionProjections` + inbox 注入（仿 agent-instructions） | 把决策**喂进后续步骤**上下文 | DSH 内已用；prac 能否挂 `agent/pre-step` **未验证**                                                                 |
| `ctx.userQuestions` / `tool-ask-user`                          | **呈现给你裁决**并喂回 loop  | 开箱即用；但被 notes 标记为「表单/追问」风险                                                                        |
| 扩 `SessionEventMap`（`decision/*`）                           | **记账**（真相源）           | 类型 merge 增强可用；DSH 的 persistence-catalog 只扫它自己 monorepo，不生成 prac 事件行                             |
| `dsh.client`（client bundle 贡献 UI）                          | 自定义 toolview / 画布渲染   | DSH 内有范例（`experimental-client-ui-agent-team`）；prac 当前 `vp pack` 只产 JS 库，无 client 构建，成本**未验证** |

**另一个值得注意的观察**：工具结果作为 `tool/result` 会**留在本会话后续上下文**（deriveMessages 保留之前的 tool call/result），所以同会话内模型能自己看到已提议的决策——C2a 甚至**不需要额外投影**，这让最小切片能非常小。

## 3. 各子决策（选项 · 代价 · 我的倾向与理由 · 留给你的判断）

### D1｜载体形态（候选决策的权威落点）

- **选项**：
  - **D1a 纯工具结果**：最省、已验证；但只是 `tool/result` 影子，非独立可裁决/可归档对象。
  - **D1b session 事件 `decision/*`**：最「正确」——真相源、可重建、可进投影/记忆；但 out-of-tree 类型增强 + 事件行不进 DSH catalog，成本最高。
  - **D1c 注入为 `UserMessage`**：进上下文最直接、本身就是已 logged 的 `user/message`；但需用 `source.kind` 区分「模型提议」vs「你已裁决」。
  - **D1d 写进 `.agents/notes/`（proposed note）再投影**：与 no-index 决策记忆天然契合；但把 harness 运行时对象与记忆格式耦合，两轨。
- **我的倾向**：session log 为**源**（D1a/D1b 起步），磁盘 notes / 画布只是**记忆与呈现投影**。
- **为什么**：prac 的原则是 harness 做「可核实的账本」，notes 做「架构记忆」；两者不应混源。账本是运行时真相，notes 是给 agent 装载的导航与给人类的呈现。让 note 当源，等于让「给人类看的文账」当「给机器算的账」——一旦笔记被编辑，模型可见性就失去可重建性。
- **留给你**：真相源你定在哪？我以上为倾向，但这是架构判断。

### D2｜模型可见的主缝

- **选项**：工具（产生）＋ 投影/注入（喂后续）＋ 事件（记账）是**协作**而非互斥。三种组合的粒度不同。
- **我的倾向**：`工具产生`为主链 + `tool/result 留上下文` 已够 C2a 用；事件记账作真相源；投影/注入留到「需要把已裁决决策明确喂回来」时再加。
- **为什么**：同会话内模型已能看到自己的工具结果（见 §2）；最小切片不用先碰 `sessionProjections`/`agent/pre-step` 这个未验证的成本。
- **留给你**：是否接受「主链 = 工具产生 + 工具结果留上下文」，把投影留到需要时再上？

### D3｜「审决策」的呈现（审查是主界面；受 §0 输入约束）

- **选项**：
  - **D3a 工具结果 render**：最便宜、已被 C1 验证；你看到「决策文档」可读不可点，裁决靠下一轮交互。
  - **D3b 自定义 client toolview**：bundle 声明 `dsh.client`，注册 `tool.call.toolview`，可做成**可展开/可批注的画布**；但 client 构建 + `dsh-client-*` peer 成本**未验证**。
  - **D3c 新 event 自定义渲染**：成本最高。
- **我的倾向**：先 D3a（render 决策文档）验证机制与手感；但**呈现形态按 §0 约束走「文档/画布」**，不追求「按钮式审批」——让模型把决策摊成一块**可读、可批注的讨论介质**，而不是多问一句。
- **为什么**：你偏好文件/画布讨论；「审决策」的本意是让人**一望即觉**地判断，而不是填表或被打断问话（notes 正是警惕「填表式追问」）。
- **留给你**：先便宜（D3a 决策文档）验证手感，还是直接上 client toolview 的画布（D3b）？两者都是「文档/画布」方向，区别在成本与交互丰富度。

### D4｜何时摊开 / 循环语义

- **选项**：
  - **D4a 目标开头一次性摊**：简单、符合 C2 直觉；但无「逐层/边做边审」。
  - **D4b 逐层展开 + 高杠杆点中断**：贴 notes「对的时机/分歧点」；但 notes 明说「目前基本没有好答案」。
  - **D4c 模型用工具主动开口**：把「先审决策」做成**有牙齿的反向约束**（必须先开决策空间才能碰文件），而非纯行为准则。
- **我的倾向**：D4a 起步 + 预埋 D4b/D4c 扩展点。
- **为什么**：D4b 一步到位会撞上「没有好答案」这个已记录的坑；先验证 D4a，再观察哪些点天然值得中断。
- **留给你**：认可 D4a 起步吗？你更想把「决不先动文件」做成「工具牙齿」（D4c）还是先靠工作纪律？

### D5｜C2 切多小 + 怎么验证

- **我的倾向**：**C2a = 一个候选决策工具（模型能「摊开决策空间」，结构化对象承载选项/代价/推荐/验证计划）→ 落成一张「决策文档」（D3a 呈现）→ 你在这份文档上裁决/批注（讨论式协作的直接落点）→ 裁决记回 log**。先不接：notes 归档投影、client toolview 画布、逐层展开。
- **为什么**：最小可验证单元（C1 哲学）；且直接把你「文件/画布讨论」的偏好落成 C2 的第一个真实产物——**你看着这份决策文档批注，就是 C2 的第一个验收**。
- **怎么验证（客观为主）**：
  1. **机制**：headless 跑，模型能调开工具（schema 进模型、调用成功、`decision/proposed` 落 log）；model-visible ⟺ logged 复核。
  2. **行为**：真实大目标下，观察「先摊决策」是否贯穿（而非直接改文件）。
  3. **手感（需你）**：用生产的大目标摊一次决策文档，你批注，判它是「便宜、高杠杆的审决策」还是「又一次仪式感」。
  4. **回归**：`prac_ping`、profile、build 不被破坏。
- **留给你**：C2a 这个切片和验证方式，你认吗？

## 4. 我真正需要你判断的（不替你拍板）

1. **真相源**（D1）：session log 为源 / notes 为源 / 先不定（C2a 用纯工具结果）。
2. **切片**（D5）：C2a 最小，还是一步带「接受→承诺→归档」闭环。
3. **呈现重度**（D3）：先便宜（D3a 决策文档）还是直接 client toolview 画布（D3b）。
4. **「先审决策」的约束强度**（D4）：靠工作纪律，还是做成「工具牙齿」（必须先开决策空间才能碰文件）。
