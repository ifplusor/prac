# Agent Note: UI resource model — category-specific CRD / CR

> **这是哪件工作**：prac UI 的声明式资源机制。它定义 core 的 CRD-lite：按 **ViewGroup / View 两个类别**分开的 definition / resource / registry / materializer。
> **关系**：UI umbrella 见 [2026-10-20-ui-framework.md](../in-progress/2026-10-20-ui-framework.md)；VS Code adaptor 见 [2026-10-17-vscode-host-architecture.md](../in-progress/2026-10-17-vscode-host-architecture.md)；container context 见 [2026-10-22-vscode-container-context.md](2026-10-22-vscode-container-context.md)。

## Summary

UI 的 CRD 不能像 Kubernetes 那样只有一个通用 resource 接口，因为 **ViewGroup 和 View 的 materialization 目标不同**：

- `ViewGroupResource` → `ViewGroup`；
- `ViewResource` → `View` / `ViewHost`。

所以 core 只共享 **CR 信封**，不共享多态 definition：

```text
ResourceEnvelope<TSpec>
  ├─ ViewGroupResource
  └─ ViewResource

ViewGroupDefinition → materialize(ViewGroupResource) → ViewGroup
ViewDefinition      → materialize(ViewResource)      → View / ViewHost
```

`vscode-host` 注册 concrete definition，产生 concrete resource：

- `VscodeViewGroupDefinition` / `VscodeViewGroup`
- `VscodeViewDefinition` / `VscodeView`

frame / arrangement 按类别使用对应 registry / materializer，不做 `category` 字段分派。

## Motivation

Kubernetes 的 CRD 是通用对象模型；UI 不是：

- view group 的产物是 group runtime / binding；
- view 的产物是 view runtime / host；
- 两者的 schema、validation、factory、生命周期形态不同；
- 如果强行共用一个 `ResourceDefinition<TSpec, TMaterialized>`，就要在运行时加 `category` 判别或 `as` 断言。

代价是两套接口，但收益是：

- 类型安全；
- 不会把 `ViewResource` 传给 `ViewGroupDefinition`；
- 不需要 `spec.category` 这种容易与 `kind` 冲突的字段；
- frame 的两条路径各自清楚。

## 1. 机制

### 1.1 CR 信封

```ts
interface ResourceEnvelope<TSpec> {
  apiVersion: string;
  kind: string;
  metadata: {
    id: string;
    labels?: Record<string, string>;
    annotations?: Record<string, string>;
  };
  spec: TSpec;
}
```

- `apiVersion + kind` 是类型；
- `metadata.id` 是身份；
- `spec` 是可变配置；
- kind 不可变；spec 可变。

### 1.2 两个类别

```ts
interface ViewGroupResource extends ResourceEnvelope<ViewGroupSpec> {}
interface ViewResource extends ResourceEnvelope<ViewSpec> {}

interface ViewGroupDefinition {
  apiVersion: string;
  kind: string;
  validate(spec: unknown): ViewGroupSpec;
  default(spec: unknown): ViewGroupSpec;
  materialize(decl: ViewGroupResource, ctx: MaterializeContext): ViewGroup;
  bindingFactory?(spec: ViewGroupSpec): GroupBinding | undefined;
}

interface ViewDefinition {
  apiVersion: string;
  kind: string;
  validate(spec: unknown): ViewSpec;
  default(spec: unknown): ViewSpec;
  materialize(decl: ViewResource, ctx: MaterializeContext): View;
  hostFactory(decl: ViewResource, options?: { move?: MoveIntent }): ViewHost;
}

interface MoveIntent {
  fromGroupId: string;
  toGroupId: string;
  reason: "user" | "layout" | "editor-split";
  preserve?: "auto" | "state" | "never";
}

interface ViewHost {
  mount(element: HTMLElement): void;
  release(): void;
  focus(): void;
  focusable: boolean;
}
```

- **没有统一的 `ResourceDefinition`**；
- `Definition = 类型 / CRD`；
- `Resource = 实例 / CR`；
- `ViewGroupDefinition` 不接收 `ViewResource`，反之亦然；
- category 由接口 / registry 决定，不是 spec 字段。

### 1.3 移动

- **默认语义是目标先建、源后释放**，不是先销毁再重建；
- `MoveIntent` 只是 hint，由 source 决定是否保留 DOM / model / viewState；
- 默认不承诺状态保留；source 可以优化；
- frame 不按 `hostKind` 或 capabilities 做移动分支；
- 目标创建失败时保留源 host。

### 1.4 registry / materializer

```ts
class ViewGroupDefinitionRegistry {
  register(def: ViewGroupDefinition): void;
  lookup(apiVersion: string, kind: string): ViewGroupDefinition | undefined;
}

class ViewDefinitionRegistry {
  register(def: ViewDefinition): void;
  lookup(apiVersion: string, kind: string): ViewDefinition | undefined;
}
```

```text
source adapter
  ├─ register ViewGroupDefinition / ViewDefinition
  ├─ emit ViewGroupResource / ViewResource
  └─ materializer
       ├─ ViewGroupResource → ViewGroup
       └─ ViewResource → View / ViewHost
```

- registry 可以共享一个泛型 helper；
- materializer 可以共享事务 / 诊断基础设施；
- 但 **definition 接口不合并**。

## 2. 资源

第一版只有两类：

| 类别 | kind | spec 子类型 | materialize |
| --- | --- | --- | --- |
| **view group** | `ViewGroup` | `groupKind: container \| editor` | `ViewGroup` |
| **view** | `View` | `spec` 由来源定义（如 `VscodeView` 的 `hostKind`） | `View` / `ViewHost` |

`vscode-host` 的具体项：

- `VscodeViewGroupDefinition` → `VscodeViewGroup`
- `VscodeViewDefinition` → `VscodeView`

```text
VscodeViewGroup
  → ViewGroupState
    → ViewGroup
      → binding?（ContainerBinding / EditorGroupBinding）

VscodeView
  → View
    → VscodeViewHost
      → ViewPane / EditorPane
```

## 3. 复杂度预算

| 保留 | 不做 |
| --- | --- |
| 2 个类别接口：ViewGroup / View | 统一多态 `ResourceDefinition` |
| 2 个 registry / materializer | 通用 resource framework |
| 1 个 CR 信封 | 任意 UI 概念都做 CRD |
| `validate` / `default` / factory 函数 | API server / etcd / watch / informer |
| 一个 declared group 最多一个 binding | controller / operator / reconcile loop 框架 |
| 一个 view 一个 view host | `status` / finalizers / ownerReferences |

- 只有 view / view group 是 CR；action / overlay / part / host 不 CRD 化。
- 不按 view 类型细拆 CRD；tree / webview / React 用来源自己的 `spec` 表达。
- **`hostKind` 是 source-owned**；core 不解析，只通过 `ViewHost` 接口认识行为。
- **移动是 source-owned**：core 传 `MoveIntent`，默认目标先建、源后释放；优化由 source 决定。
- 一个 group 只有一个 declaration 来源。
- 第一版不做多版本转换；只保留 `apiVersion`。
- 两个 registry / materializer 可以共享泛型工具，但不能共享多态 definition。

## 4. 生命周期

- **正常启动**：source 注册两类 definition，产生对应 resource；materializer 产出 runtime。
- **recovery**：definition / resource 由 source 重建；runtime 不持久化；layout / `ContainerRecord` 从 layout store 恢复。
- **动态安装**：新 definition / resource 进入对应 registry；materialize。
- **卸载 / reload**：resource 消失；runtime 释放；placement 可 tombstone。
- **不根据 group 内容推断 kind**；group / view 各自从 declaration 得到类型。

## 5. Open questions

1. **registry / materializer API**：是否共享泛型 registry helper；materialize 是否允许异步。
2. **schema / validation**：只用 TypeScript 函数，还是需要可序列化 schema。
3. **版本**：`apiVersion` 是否做多版本转换；第一版不做。
4. **拆 CRD**：`ViewGroup` 的 container / editor 是否最终拆成两个 kind；`View` 是否按 host 行为拆。
5. **持久化**：哪些 materialized 结果进 layout store；`ContainerRecord` 是否唯一持久化记录。
6. **隔离**：definition / factory 失败是否只影响自己的 resource。
