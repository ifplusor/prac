# Agent Note: 视图的隔离与对等 —— 区域骨架、视图是单位

> **来源**：2026-10-05 讨论。James：「以插件式思维在 layout 上做隔离，如使用 shadow dom」，随后纠正：***整个 ui 框架应该归属于 prac，我们会从 dsh 和 vscode 中借用或借鉴一些现成的组件。***
> **口径来源**：`docs/architecture.md` §3.1、[2026-09-19-architecture.md](../in-progress/2026-09-19-architecture.md)、[2026-09-13-vs-concept-boundary.md](../in-progress/2026-09-13-vs-concept-boundary.md)（"机制不认识来源词"、"容纳单位 = 视图"），以及两条 superseded 的设计（09-15 / 09-16）。

## Problem

prac 的框架声称「区域树、编排、层级、浮层」都归自己（`docs/architecture.md` §3.1）。但只要盒子里的东西**自带全局样式系统、或自带一套浮层模型**，这句话就有一个未定义的空洞：

> **框架对"盒子里的东西"负什么责？**

此前没有原则回答它，于是"能住下"是靠逐处局部处置维持的（一处管几何、一处管样式、一处管浮层锚点）。**这些处置不是病根，病根是没有原则**；它们只是原则缺席时，每个面逐个被临时补上的痕迹。

## 设计

**布局由 prac 拥有**：区域树、编排、层级、浮层都是框架自己的。**视图是布局里的单位，按窗口的方式来管**——独立、可在区域之间移动、各有各的状态。

### 区域是骨架，视图是单位

| 概念 | 是什么 | 职责 |
| --- | --- | --- |
| **区域**（基础区域 / 悬浮层 / 子区域） | **骨架**：可嵌套、可分栏分列（`stage` 是这一层的一个区域） | 划分空间、给视图盒子 |
| **视图** | 被摆放、被拖动、被隔离的**单位** | 内容与它自己的内部 |
| **悬浮层** | **顶层的一个区域** | 住框架级的视图（命令、通知等） |

- **视图住在区域里**；进 layout 就是进某个区域，区域给它盒子。
- **视图的拖放 = 在区域之间搬视图**；迁移的单位就是它。**分栏** = 区域再分出一个子区域，子区域里放视图。
- **视图内部没有第二个 stage，也没有自己的区域树**；视图内部只有它自己。
- **视图之间、区域之间都对等**：同一种对象、同一套契约；机制**按注册表成员认识视图，不认识来源**（`2026-09-13` 已裁）。区域之间的差别只在**命名层绑给它的模式集合与默认模式**，不是特权。

### 隔离与对等（对所有视图）

- **所有挂在 layout 中的视图都隔离**：隔离是**结构性质**，不是给某一类内容开的特例（**作用域不止于浮层**）。
- **所有视图都对等**，两层：**边界上对等**——每个都是一样的隔离盒子、同一份契约、同一套保证，没有特权视图、没有例外；**对待上对等**——机制不认识它的来源。
- **框架不伸手进视图内部**：凡要跨边界生效的（主题、焦点、样式），都必须是对所有视图一致的**显式通路**。
- **框架拥有区域，不拥有视图内部**：分栏、拖放、迁移都落在区域这一级——"对等"说的是**每个区域里一视同仁**，不是所有视图长得一样。

### 隔离的保证与形态

- **保证归框架**："每个视图都被隔离"是**框架的事**，不是内容自愿配合的结果——否则它就不是保证。因此**隔离不由视图选择**（否则又出现"我不用隔离"的例外，统一性当场破掉）。
- **形态可以有多种**：按**内容的性质**选实现——DOM 内容用影子域、自成体系的内容用独立浏览上下文（webview 本来就是这一种），将来还可能有别的。**形态是实现，不是契约**。
- **形态的选择权在框架**：选哪种由**框架**按内容决定，并把结果**记录在视图的身份里**（持久化与调试都要知道它是哪一种）。内容不需要知道，也不需要声明。
- ⇒ 契约只有一句：**"你被隔离，且我的接口对所有隔离形态一致。"** 上面那张不变量表（G1–G3）就是这个接口的形状。

### 布局模式与区域名绑定

**基础层只有三种模式；叠放只在悬浮层：**

| 模式 | 形状 | 同一块矩形里同时显示几个 | 需要层序吗 | 在哪一层 |
| --- | --- | --- | --- | --- |
| **分区** | 区域分出子区域 | 各占一块，互不重叠 | 不需要 | 基础层 |
| **顺序**（`stack`） | 一条轴上依次排开 | 各占一段，互不重叠 | 不需要 | 基础层 |
| **选择**（`tab`） | 同一块矩形，取其一 | **一个** | 不需要 | 基础层 |
| **叠放** | 同时可见、需要定序 | **多个** | **需要** | **只有悬浮层** |

- **叠放 = 同时可见 + 需要定序**；tab 同一时刻只显示一个 ⇒ 定序没有对象 ⇒ **tab 属"选择"，不是叠放**。
- **基础层不需要 z 序**："现在显示哪一个"是**选中**的问题——它是布局的**状态**（持久化），走注意力只是**改变它的交互过程**。
- **框架的装饰单列**：sash、拖拽落点提示、焦点环这类画在内容之上的东西，是**框架自己的装饰**，与内容不同类、不参与内容层序（防止"反正有东西画在上面"被拿来当理由，把内容叠放引回基础层）。

**区域 = 一组视图，模式由"命名区域"绑定：**

| 区域名 | 分区（拆子区域） | `stack`（顺序） | `tab`（选择） | 默认模式 | 状态 |
| --- | --- | --- | --- | --- | --- |
| `stage` | 有 | **无** | 有 | `tab` | 已定 |
| `bottom` | **无** | **无** | 有 | `tab` | 待确认 |
| `leftbar` / `rightbar` | **无** | 有 | 有 | `stack` | 待确认 |

- **机制提供模式集合**（它认识 `stack` / `tab` / 分区）；**区域名绑定"可用哪些 + 默认哪个"**。两者分开，所以"区域对等"与"各区域不一样"不再打架；**这张表是数据，不是特权**。
- **区域名是设计层的名字，与来源无关**：`leftbar` / `rightbar` 是**位置的对称命名**；DSH 那边的槽名（`sidebar`）与 VS Code 那边的部件 id（`workbench.parts.sidebar`）是**借来的名字**，不在这一层出现。
- **每个子区域跟随它所在区域名的绑定**（`stage` 拆出来的每块都有 `tab`、都不能 `stack`）。
- **tab 是区域级的**，不是 stage 专有。
- **一个派生要求**：视图在区域之间搬时，**目标区域可能不支持它来源处的模式**；这要求**视图的呈现与它所属的分组解耦**——分组决定怎么显示，视图只管内容。不成立的话，视图就不能真正自由搬运。

### 视图的状态

- **"选中"是 UI 状态，属于持久化**（它归框架，不归注意力）。
- **持久化该有的**：视图在哪个区域、组内顺序、折叠、在屏上、每个组的选中项、区域用的模式；**不该有的**：区域内的层序、注意力栈、返回栈。

### 借用件的 adaptor

**框架只提供隔离本身，不认识任何来源词**。VS Code 那一侧的专有知识——`monaco-workbench` 类、`--vscode-*` 变量、上游样式表、它自己的浮层模型——**全部收在 `vscode-host` 这一层**（机制侧落在 `vendor/vscode-embed`，政策在插件行）：

- **框架侧**：给每个视图一个盒子、一个隔离边界（影子根），到此为止。**它不知道里面是 VS Code**，也不需要"沙箱槽"这类特殊槽——**就是普通槽 + 宿主元素**。
- **adaptor 侧**：把上游那几样东西投进边界内——**规则表照原样投**、**主题变量以 `:host` 作用域投**（**不用**包装类：实测那会唤醒整个 workbench 作用域的级联）。**浮层按作用域分**：只在视图盒子里浮的（webview 的 overlay、视图自己的悬停 / 局部菜单）**是视图自己的事**——视图自闭环，而且**同树才能用 CSS 锚点定位**（实验 7：锚点在影根里、浮层在文档里 → 不解析）；**框架接管的是全局、不在任何视图里的悬浮**（如阻止整个应用的模态框、命令面板、通知）。桥的两条路要分清：整部件走 `partHost`（宿主带 `[data-vscode-embed-part-host]`），VS Code 的**视图**（explorer 等）走 `mountViewInto`（宿主是 `[data-vscode-embed-view]`）。
- ⇒ **机制不做特例，来源词也不外溢**：`monaco-workbench` 从"宿主侧要镜像的类"变成**adaptor 内部的事**。

### 常驻视图与即显即隐的视图

- **常驻视图**：布局的成员，有身份、有位置，**进持久化**。
- **即显即隐的视图**：**右键菜单、命令面板、通知**这类——一次交互里出现、用完（选中一项 / 点外 / 失焦）就消失，**不进持久化**、不占布局的持久结构。**工具提示、补全列表、就地编辑的小浮层**同属这一类。
- **两者是同样的视图、同样的隔离契约**（各有自己的盒子，出不了盒子）；差别在生命周期与是否进持久化。
- **框架 chrome 是唯一的例外**：sash、拖拽落点提示、焦点环不是视图，是框架的装饰（见上）。

**与这些设计冲突、已作废的说法**：按内容性质或来源给视图分类；"区域与悬浮层是两类东西"；"容器既给几何、又是被摆弄的单位"；"tab 是 stage 的能力"；"选中归注意力、因此不持久化"；"**右键菜单这类界面不是视图、可以留在视图的盒子里**"。

## 主命题与三条不变量

> **layout 给每一个视图一个隔离盒子，并且所有视图对等。**

| # | 不变量 | 谁保证 | 状态 |
| --- | --- | --- | --- |
| G1 | 每个视图有真实几何（有尺寸，且随区域变化） | 框架（区域） | 未声明 |
| G2 | 视图里的样式出不了它的盒子，也不因缺上下文而失效 | 框架的边界（统一） | 未声明 |
| G3 | **凡"生在 A、要出现在 B"的东西，走显式通路，由 B 落位与定序；视图不能自己画到外面** | 框架 | 由已定的设计推出 |

**G2 需要 G1 才能成立，G3 需要 G1 与 G2 一起。** 这解释了为什么逐处处置总是按下葫芦浮起瓢：几何没给对时，样式与浮层的问题会被伪装成"样式没进来"或"浮层不见了"（命令面板那次，现象是"打不开"，根因是几何）。

**层级两段，选中独立**：**区域之间的层序**归框架（基础区域与悬浮层之间只有这一张表）；**视图内部的层序**归视图自己；**选中**是第三件事——点一下不改变层序。三者分开：**层序持久化、选中也持久化，而"走神去看了什么"（注意力 / 返回栈）不持久化。**

## 还没定的

- **隔离形态的对应规则**：契约只要求"边界统一、强制、视图内部无感"（见"隔离的保证与形态"）；"哪种内容用哪种形态"尚未定。**代价表已按实验定下来**（实验 1–4，含真 rig 走 bridge），逐根投放是**三件事**：① **规则表照原样投**（document 的规则不作用于影子树）；② **主题变量以 `:host` 作用域投**——**不要**用 `monaco-workbench` 包装去拿变量，实测那会把整条 workbench 作用域的级联唤醒、**画面整体变样**（真 rig：134960/134960 像素全变）；③ **活的订阅**，不是死拷贝（主题那张表被原地改写）。三样都便宜，且**不需要上游补丁**。
- **哪些界面由框架创建**：判据是**作用域**——**全局、不在任何视图里**的（阻止整个应用的模态框、命令面板、通知）归框架；**只在视图盒子里浮的**归视图自己（自闭环）。悬停提示 / 补全列表 / 就地小浮层这类落在后者的哪一边，逐个归类即可，不再需要一条新判据。
- **坐标空间**：锚点用什么表达（frame 的布局坐标 vs 视图内坐标 + 变换），以及**锚点失效与跟随**的规则（谁算、何时失效、随滚动与尺寸变化怎么办）。
- **命名**：常驻之外的这类视图取什么称法，**待定**。
- **adaptor 与框架之间那条边的形状**：框架给盒子与边界，adaptor 往里投样式与承载；两者之间要不要一条显式接口（谁告诉 adaptor"这个盒子的根在哪"），还是 adaptor 自己认？**待定**。
- **借用件那条边的做法**：借用件的浮层**不越出视图盒子**的留在它自己的根里（同树、锚点能用、内容与行为都不用改）；**全局的**才由 adaptor 交给框架。剩下待定的是"**视图内部的面要越出盒子时怎么办**"——就地翻转留在盒内，还是走框架（那就要**锚点矩形**，实验 7）。

## 菜单、命令面板、通知：由框架提供机制

这类界面**也是视图**（见"常驻视图与即显即隐的视图"），只是**由框架按需创建**——**不是一种新东西**。视图不该各自造一套菜单：既不可能一致，也拿不到平台该给的东西。

**框架提供的是"怎么显示"的机制**，不是内容：视图（或它内部的元素）只**声明**（菜单项 / 命令 / 通知），**呈现统一归框架**——定位、翻转与贴边、关闭（点外 / Esc / 失焦）、键盘可达、层序。

**先例**：VS Code 与 Chrome 的右键菜单都不是自己画的——它们用 **macOS 系统提供的菜单**（同一条路在别处映射到平台的菜单实现）。"菜单"是**平台 / 宿主**该提供的东西。

**锚点不是"跨视图通路"，是一个位置参数**：框架在悬浮层里创建这个视图，位置**用框架提供的坐标空间**算出来。所以不需要任何特别的通道——只是**创建视图 + 一套坐标**。

**借用件里只有全局的那些走这条**：命令面 / 通知这类由 adaptor 交给框架；**只在它自己盒子里浮的（webview 的 overlay、局部菜单、悬停）留在它自己的根里**——那不是"自绘一套菜单"，而是视图的内部（同树才能锚定，实验 7）。

## 边界带来的新代价

- **每个视图都付边界成本**：调试多展开一层；可达性结构会变；样式"广播式生效"没了。以前只有"重"的视图付，现在轻量的也付——**这是"对等"的代价，也是它的价值**（没有第二种规矩）。
- **主题与样式必须走显式通路**：把"样式怎么流"从"碰巧能继承"升级成**契约**。
- **`prac.view` 的含义扩了**：原来只表示"装一个视图宿主"，现在还要携带它在布局里的身份与边界。这是视图契约的实质扩张。

## 契约写死之前必须先验的三件

1. ~~主题与样式能否跨过统一隔离边界~~ **已验（六道）**：① 合成——`:root` 级变量会继承、`monaco-workbench` 上的不会、document 规则不作用于影子树；② **真部件**——`workbench.parts.sidebar` 搬进影子根后**像素零差**（147680 像素全同）；③ **换主题**——死拷贝会陈旧、**盯源表改写再重投跟得上**（零补丁）；④ **真 rig 走 embed bridge**——视图宿主搬进影子根后同样**像素零差**（134960 像素全同），并由此定下"**变量走 `:host`、不走包装类**"这条配方。**配方与读数在记录里。**两条挂载路各有证据：**视图路**在真 rig 上验（实验 4），**整部件路**在独立查看页上验（实验 2 + 实验 6A：用库真实的宿主形状 + 配方 = 像素零差）——后者在 rig 里**没有消费者**（编排只注册了 `vscode:sidebar`），要等有视图映射到 part 时再补。**还剩**：换主题的**画面**是否跟着变——变量被原地改写、订阅看得见已验；但实验 6 证明**不能靠改一个变量来判断**（连在文档里改主题表里的变量都不改画面，且页面上有 `contributedColorTheme`（1013 条）与另一张 2284 条两张变量表并存）⇒ 这条要**真的切一次主题**、或实现之后端到端按**画面**验。
2. **区域有真实几何时，进入悬浮层的东西是否自然落对**——命令面板那次的现象（几何为 0）是不是全部。
3. **统一隔离对轻量内容的实测代价**——数字出来之前，"所有视图对等"是原则，不是已被证明可行的原则。

## 开放问题（分成三类）

**必须在定契约前知道**："还没定的"那几条，以及上面三件。

**接受这个方向之后要背的债（不阻塞）**：边界上的可达性；边界的调试成本；轻量内容的额外开销。

**另案（不属于这个工作）**：两侧散落的层号要不要收敛成一张表。按本模型它变成"**区域之间那张唯一层序表**"的问题；它仍是独立的一件事，塞进来会把它变成布局契约的附属条件。

## 一个需要先解决的用词冲突

这里与 `docs/architecture.md` §3.1 都用"沙箱"指**组件级隔离**，而 prac 既有材料里"沙箱"一律指 **agent 运行时的执行沙箱**——这里已改用"隔离 / 影子槽"一类的词，`§3.1` 同步时一并清。
