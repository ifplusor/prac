# Agent Note: 视图的隔离与对等 —— 区域骨架、视图是单位

> **来源**：2026-10-05 讨论。James：「以插件式思维在 layout 上做隔离，如使用 shadow dom」，随后纠正：***整个 ui 框架应该归属于 prac，我们会从 dsh 和 vscode 中借用或借鉴一些现成的组件。***
> **口径来源**：`docs/architecture.md` §3.1、[2026-09-19-architecture.md](../in-progress/2026-09-19-architecture.md)、[2026-09-13-vs-concept-boundary.md](../in-progress/2026-09-13-vs-concept-boundary.md)（"机制不认识来源词"、"容纳单位 = 视图"），以及两条 superseded 的设计（09-15 / 09-16）。

## Problem

prac 的框架声称「区域树、编排、层级、浮层」都归自己（`docs/architecture.md` §3.1）。但只要盒子里的东西**自带全局样式系统、或自带一套浮层模型**，这句话就有一个未定义的空洞：

> **框架对"盒子里的东西"负什么责？**

此前没有原则回答它，于是"能住下"是靠逐处局部处置维持的（一处管几何、一处管样式、一处管浮层锚点）。**这些处置不是病根，病根是没有原则**；它们只是原则缺席时，每个面逐个被临时补上的痕迹。

## 设计

**布局由 prac 拥有**：区域树、编排、层级、浮层都是框架自己的。**视图是布局里的单位，按窗口的方式来管**——独立、可在区域之间移动、各有各的状态。

### 区域是骨架，视图是单位

| 概念 | 是什么 | 职责 |
| --- | --- | --- |
| **区域**（基础区域 / 悬浮层 / 子区域） | **骨架**：可嵌套、可分栏分列（`stage` 是这一层的一个区域） | 划分空间、给视图盒子 |
| **视图** | 被摆放、被拖动、被隔离的**单位** | 内容与它自己的内部 |
| **悬浮层** | **顶层的一个区域** | 住框架级的视图（命令、通知等） |

- **视图住在区域里**；进 layout 就是进某个区域，区域给它盒子。
- **视图的拖放 = 在区域之间搬视图**；迁移的单位就是它。**分栏** = 区域再分出一个子区域，子区域里放视图。
- **视图内部没有第二个 stage，也没有自己的区域树**；视图内部只有它自己。
- **视图之间、区域之间都对等**：同一种对象、同一套契约；机制**按注册表成员认识视图，不认识来源**（`2026-09-13` 已裁）。区域之间的差别只在**命名层绑给它的模式集合与默认模式**，不是特权。

### 隔离与对等（对所有视图）

- **所有挂在 layout 中的视图都隔离**：隔离是**结构性质**，不是给某一类内容开的特例（**作用域不止于浮层**）。
- **所有视图都对等**，两层：**边界上对等**——每个都是一样的隔离盒子、同一份契约、同一套保证，没有特权视图、没有例外；**对待上对等**——机制不认识它的来源。
- **框架不伸手进视图内部**：凡要跨边界生效的（主题、焦点、样式），都必须是对所有视图一致的**显式通路**。
- **框架拥有区域，不拥有视图内部**：分栏、拖放、迁移都落在区域这一级——"对等"说的是**每个区域里一视同仁**，不是所有视图长得一样。

### 隔离的保证与形态

- **保证归框架**："每个视图都被隔离"是**框架的事**，不是内容自愿配合的结果——否则它就不是保证。因此**隔离不由视图选择**（否则又出现"我不用隔离"的例外，统一性当场破掉）。
- **形态可以有多种**：按**内容的性质**选实现——DOM 内容用影子域、自成体系的内容用独立浏览上下文（webview 本来就是这一种），将来还可能有别的。**形态是实现，不是契约**。
- **形态的选择权在框架**：选哪种由**框架**按内容决定，并把结果**记录在视图的身份里**（持久化与调试都要知道它是哪一种）。内容不需要知道，也不需要声明。
- **盒子是硬边界，由框架强制**：宿主同时是绝对**与**固定定位后代的包含块，并裁到盒内 ⇒ **视图画不到自己的盒子外面**。要出现在盒外的，只能走框架的悬浮层。这条是 G3 的强制手段（见「边界带来的新代价」）。
- ⇒ 契约只有一句：**"你被隔离，且我的接口对所有隔离形态一致。"** 上面那张不变量表（G1–G3）就是这个接口的形状。

### 布局模式与区域名绑定

**基础层只有三种模式；叠放只在悬浮层：**

| 模式 | 形状 | 同一块矩形里同时显示几个 | 需要层序吗 | 在哪一层 |
| --- | --- | --- | --- | --- |
| **分区** | 区域分出子区域 | 各占一块，互不重叠 | 不需要 | 基础层 |
| **顺序**（`stack`） | 一条轴上依次排开 | 各占一段，互不重叠 | 不需要 | 基础层 |
| **选择**（`tab`） | 同一块矩形，取其一 | **一个** | 不需要 | 基础层 |
| **叠放** | 同时可见、需要定序 | **多个** | **需要** | **只有悬浮层** |

- **叠放 = 同时可见 + 需要定序**；tab 同一时刻只显示一个 ⇒ 定序没有对象 ⇒ **tab 属"选择"，不是叠放**。
- **基础层不需要 z 序**："现在显示哪一个"是**选中**的问题——它是布局的**状态**（持久化），走注意力只是**改变它的交互过程**。
- **框架的装饰单列**：sash、拖拽落点提示、焦点环这类画在内容之上的东西，是**框架自己的装饰**，与内容不同类、不参与内容层序（防止"反正有东西画在上面"被拿来当理由，把内容叠放引回基础层）。

**区域 = 一组视图，模式由"命名区域"绑定：**

| 区域（位置） | 分区（拆子区域） | `stack`（顺序） | `tab`（选择） | 默认模式 | 状态 |
| --- | --- | --- | --- | --- | --- |
| `left` | **无** | 有 | 有 | `stack` | 待确认 |
| `right` | **无** | 有 | 有 | `stack` | 待确认 |
| `stage` | 有 | **无** | 有 | `tab` | 已定 |
| `bottom` | **无** | **无** | 有 | `tab` | 待确认 |

**区域是位置，角色是角色——两者分开**（VS Code 自己就是这么分的：`workbench.sideBar.location` 让 primary 侧栏可以放左或放右）：

| 角色 | 绑到谁 | 借的是谁的名 |
| --- | --- | --- |
| `primarySidebar` | DSH 的 `dsh:sidebar` | VS Code：Primary Side Bar |
| `secondarySidebar` | DSH 的 `dsh:rightbar` | VS Code：Secondary Side Bar（`ViewContainerLocation.AuxiliaryBar`） |

- **机制提供模式集合**（它认识 `stack` / `tab` / 分区）；**区域名绑定"可用哪些 + 默认哪个"**。两者分开，所以"区域对等"与"各区域不一样"不再打架；**这张表是数据，不是特权**。
- **两个层次要分清（落地时容易混）**：**角色**是 prac 的词，用**平台的角色名** `primarySidebar` / `secondarySidebar`（`RoleBindings`，代码里已改）——位置中立，因为上游允许 primary 侧栏换边；**区域 id** 是**位置**词 `left` / `right`（不改，改它要升持久化 key）；**借来的名字不动**（`dsh:sidebar` 是 DSH 那个叫 `sidebar` 的槽、`vscode:sidebar` 指 VS Code 的 sidebar、`workbench.parts.sidebar` / `workbench.parts.auxiliarybar` 是上游部件 id）。
- **区域名是设计层的名字，与来源无关**：`left` / `right` / `stage` / `bottom` 是**位置**；DSH 那边的槽名（`sidebar`）与 VS Code 那边的部件 id（`workbench.parts.sidebar`）是**借来的名字**，不在这一层出现。
- **每个子区域跟随它所在区域名的绑定**（`stage` 拆出来的每块都有 `tab`、都不能 `stack`）。
- **tab 是区域级的**，不是 stage 专有。
- **一个派生要求**：视图在区域之间搬时，**目标区域可能不支持它来源处的模式**；这要求**视图的呈现与它所属的分组解耦**——分组决定怎么显示，视图只管内容。不成立的话，视图就不能真正自由搬运。

### 不继承 VS Code 的布局复杂度

上游的布局树比我们的大（primary sidebar 里还有 activity bar、它的 position 有 top/bottom/hidden；一个 sidebar 有**多个 tab、tab 里再是 stack**；bottom 是 **Panel**，位置能绕 editor 的 top/left/right/bottom）。**分类之后大半不必继承**：

| 上游的东西 | 它其实属于 | 我们的处理 |
| --- | --- | --- |
| activity bar 及其 position、sidebar 的 tab 套 stack | **借用件的内容**（容器树） | 不继承——它在那个视图**盒子里**（隔离之后更是如此） |
| primary / secondary sidebar | **角色** | 借它的**名**（`primarySidebar` / `secondarySidebar`） |
| 两个侧栏一左一右 | **位置** | 已有：区域 `left` / `right` |
| Panel 的 top/left/right/bottom | **摆放** | 不需要 `panel.position` 这个概念——**把那个视图搬到别的区域**就行（任意方向分栏已支持） |

⇒ 上游的复杂仍然是复杂，但它**留在盒子里**，不是我们布局模型的复杂度。**唯一需要时再加的是"一级还是两级"**：我们机制现在只有一级（区域内 `tab` **或** `stack`），而借用件自带的那层（tab 套 stack）在盒内；我们自己的视图又少又平，**没有真实需求就不加第二级**。

### 视图的状态

- **"选中"是 UI 状态，属于持久化**（它归框架，不归注意力）。
- **持久化该有的**：视图在哪个区域、组内顺序、折叠、在屏上、每个组的选中项、区域用的模式；**不该有的**：区域内的层序、注意力栈、返回栈。

### 借用件的 adaptor

**框架只提供隔离本身，不认识任何来源词**。VS Code 那一侧的专有知识——`monaco-workbench` 类、`--vscode-*` 变量、上游样式表、它自己的浮层模型——**全部收在 `vscode-host` 这一层**（机制侧落在 `vendor/vscode-embed`，政策在插件行）：

- **框架侧**：给每个视图一个盒子、一个隔离边界（影子根），到此为止。**它不知道里面是 VS Code**，也不需要"沙箱槽"这类特殊槽——**就是普通槽 + 宿主元素**。
- **adaptor 侧**：把上游那几样东西投进边界内——**规则表照原样投**、**主题变量以 `:host` 作用域投**（**不用**包装类：实测那会唤醒整个 workbench 作用域的级联）。**浮层按作用域分**：只在视图盒子里浮的（webview 的 overlay、视图自己的悬停 / 局部菜单）**是视图自己的事**——视图自闭环，而且**同树才能用 CSS 锚点定位**（实验 7：锚点在影根里、浮层在文档里 → 不解析）；**框架接管的是全局、不在任何视图里的悬浮**（如阻止整个应用的模态框、命令面板、通知）。桥的两条路要分清：整部件走 `partHost`（宿主带 `[data-vscode-embed-part-host]`），VS Code 的**视图**（explorer 等）走 `mountViewInto`（宿主是 `[data-vscode-embed-view]`）。
- **adaptor 与框架之间没有显式接口**：框架给盒子与边界，adaptor 从元素自己认它的根（`getRootNode()`）——根就长在元素上，再加一条"谁告诉谁"的边只是多一层；等出现第二个 adaptor 再抽。
- **借用件的浮层现在还不在边界内**（未落地）：工作台的 boot 根挂在 `document.body`（0×0），`.monaco-workbench` 在它里面；被搬进视图影根的只有**部件**，VS Code 自己的浮层容器（`.context-view`、quick input）**留在 document**——既不被边界裁，也不被框架管。「局部浮层进视图自己的根、全局交给框架」这半仍是待做。
- ⇒ **机制不做特例，来源词也不外溢**：`monaco-workbench` 从"宿主侧要镜像的类"变成**adaptor 内部的事**。

### 常驻视图与即显即隐的视图

- **常驻视图**：布局的成员，有身份、有位置，**进持久化**。
- **即显即隐的视图**（这类视图叫**浮层视图**）：**右键菜单、命令面板、通知**这类——一次交互里出现、用完（选中一项 / 点外 / 失焦）就消失，**不进持久化**、不占布局的持久结构。**工具提示、补全列表、就地编辑的小浮层**同属这一类。
- **两者是同样的视图、同样的隔离契约**（各有自己的盒子，出不了盒子）；差别在生命周期与是否进持久化。
- **框架 chrome 是唯一的例外**：sash、拖拽落点提示、焦点环不是视图，是框架的装饰（见上）。

**与这些设计冲突、已作废的说法**：按内容性质或来源给视图分类；"区域与悬浮层是两类东西"；"容器既给几何、又是被摆弄的单位"；"tab 是 stage 的能力"；"选中归注意力、因此不持久化"；"**右键菜单这类界面不是视图、可以留在视图的盒子里**"。

## 主命题与三条不变量

> **layout 给每一个视图一个隔离盒子，并且所有视图对等。**

| # | 不变量 | 谁保证 | 状态 |
| --- | --- | --- | --- |
| G1 | 每个视图有真实几何（有尺寸，且随区域变化） | 框架（区域） | 未声明 |
| G2 | 视图里的样式出不了它的盒子，也不因缺上下文而失效 | 框架的边界（统一） | 未声明 |
| G3 | **凡"生在 A、要出现在 B"的东西，走显式通路，由 B 落位与定序；视图不能自己画到外面** | 框架（盒子的硬边界） | 已由框架强制 |

**G2 需要 G1 才能成立，G3 需要 G1 与 G2 一起。** 这解释了为什么逐处处置总是按下葫芦浮起瓢：几何没给对时，样式与浮层的问题会被伪装成"样式没进来"或"浮层不见了"（命令面板那次，现象是"打不开"，根因是几何）。

**层级两段，选中独立**：**区域之间的层序**归框架（基础区域与悬浮层之间只有这一张表）；**视图内部的层序**归视图自己；**选中**是第三件事——点一下不改变层序。三者分开：**层序持久化、选中也持久化，而"走神去看了什么"（注意力 / 返回栈）不持久化。**

## 这一轮定下的

- **隔离形态的对应规则**：契约只承诺**"框架保证隔离，且接口对所有形态一致"**（见"隔离的保证与形态"）；形态规则表**等第二种形态真出现再写**。现在落地的只有影子根，webview 本来就是独立浏览上下文、框架不用动作。逐根投放的配方是三件事：① **规则表照原样投**（document 的规则不作用于影子树）；② **主题变量以 `:host` 作用域投**（**不要**用 `monaco-workbench` 包装：实测那会唤醒整条 workbench 作用域的级联、画面整体变样）；③ **活的订阅**，不是死拷贝（主题那张表被原地改写）。三样都便宜，且不需要上游补丁。
- **哪些界面由框架创建**：判据是**作用域**——**全局、不在任何视图里**的（阻止整个应用的模态框、命令面板、通知）归框架的悬浮层；**只在视图盒子里浮的**（悬停提示、补全列表、就地小浮层、webview 的 overlay）归**视图自己**（自闭环）。
- **坐标空间：先只做无锚点的全局面**。上面那三个全局面（模态 / 命令面板 / 通知）**都不需要回到某个视图内的锚点**，由框架在悬浮层里按"居中 / 贴角"摆即可；有锚点的面都生在视图内、同树可用 CSS 锚点定位。**坐标空间（锚点矩形 + 失效/跟随规则）等真出现"必须跨视图锚定"的面再引入**——不为不存在的分支写契约。
- **盒子是硬边界**：视图内部的面**不能越出盒子**（框架裁）。所以"越出盒子"不是视图的选项，而是一个**需求**——真需要时它必须走框架的悬浮层，那时才跟坐标空间打交道。
- **这类视图叫浮层视图**（见"常驻视图与即显即隐的视图"）。
- **adaptor 与框架之间没有显式接口**：adaptor 从元素自己认根。

## 还没落地的

- **借用件的浮层路由**：借用件的浮层**不越出视图盒子**的留在它自己的根里（同树、锚点能用、内容与行为都不用改）；**全局的**才由 adaptor 交给框架。**现状不在边界内**——借用件自己的浮层容器还留在 document（见"借用件的 adaptor"）。
- **框架的锚点通路**（锚点矩形 + 落位 / 失效 / 跟随）：被"盒子是硬边界"逼出来的那条路，但按上面的裁决**先不做**；等真出现必须跨视图锚定的面再说。
- **悬停 / 补全 / 就地小浮层的逐个归类**：判据已定（作用域），落到具体面时逐个归即可。

## 菜单、命令面板、通知：由框架提供机制

这类界面**也是视图**（见"常驻视图与即显即隐的视图"），只是**由框架按需创建**——**不是一种新东西**。视图不该各自造一套菜单：既不可能一致，也拿不到平台该给的东西。

**框架提供的是"怎么显示"的机制**，不是内容：视图（或它内部的元素）只**声明**（菜单项 / 命令 / 通知），**呈现统一归框架**——定位、翻转与贴边、关闭（点外 / Esc / 失焦）、键盘可达、层序。

**先例**：VS Code 与 Chrome 的右键菜单都不是自己画的——它们用 **macOS 系统提供的菜单**（同一条路在别处映射到平台的菜单实现）。"菜单"是**平台 / 宿主**该提供的东西。

**锚点不是"跨视图通路"，是一个位置参数**：框架在悬浮层里创建这个视图，位置用框架的坐标算出来。**先只做不需要锚点的那些**（居中 / 贴角，如命令面板与通知）；锚点类（菜单、悬停）留在视图内、同树用 CSS 锚点定位——**坐标空间等真出现"必须跨视图锚定"的面再引入**。

**借用件里只有全局的那些走这条**（未落地）：命令面 / 通知这类由 adaptor 交给框架；**只在它自己盒子里浮的（webview 的 overlay、局部菜单、悬停）留在它自己的根里**——那不是"自绘一套菜单"，而是视图的内部（同树才能锚定，实验 7）。现状是两者都还在 document 的 boot 根里（见"借用件的 adaptor"）。

## 边界带来的新代价

- **每个视图都付边界成本**：调试多展开一层；可达性结构会变（焦点成两层链）；样式"广播式生效"没了。以前只有"重"的视图付，现在轻量的也付——**实测的形态是每个视图一整份 head 的样式重复（122 节点 / 653 KB）**，CPU 可忽略。**这是"对等"的代价，也是它的价值**（没有第二种规矩）。
- **主题与样式必须走显式通路**：把"样式怎么流"从"碰巧能继承"升级成**契约**。
- **`prac.view` 的含义扩了**：原来只表示"装一个视图宿主"，现在还要携带它在布局里的身份与边界。这是视图契约的实质扩张。
- **盒内浮层只能在盒内翻**：盒子是硬边界（框架裁），所以"浮层越出盒子"不是视图自己能解决的事——要么就地翻转、夹在盒内，要么走框架的悬浮层。借用件那些默认会越界的局部面（窄盒里的菜单）因此要 adaptor 参与。

## 契约写死之前必须先验的三件（已全过）

1. **主题与样式能跨过统一隔离边界**：`:root` 级变量继承、外层类上的不继承、document 规则不作用于影子树；真部件与真 rig 上的视图宿主搬进影子根都**像素零差**；换主题是**原地改写**源表，**盯源表重投**跟得上（零补丁），且**真的切一次主题时画面跟着变**。配方：**规则表照原样投、变量以 `:host` 作用域投**（不用 `monaco-workbench` 包装——实测它会唤醒整条级联、画面整体变样），**活的订阅**。两条挂载路都验过（视图路在真 rig，整部件路在独立查看页 + rig 补验）。
2. **区域有真实几何时，进入悬浮层的东西自然落对**：命令面板那次的根因就是几何（0×0），给 boot 容器与视口几何后它正常渲染。⇒ 浮层落位不是"放哪"的问题，是**几何**的问题，这条已是全部。
3. **统一隔离对轻量内容的实测代价**：代价是**样式在 DOM 里的线性重复**——每个视图一整份 head（默认编排下 **122 个样式节点 / 653 KB / 13,502 条规则**，每多一个视图严格 +1 份）；**CPU 代价可忽略**（镜像亚毫秒、同步一帧内、挂载十几毫秒）；**可达性与键盘未被破坏**（a11y 树穿透影根、首次 Tab 即进根），唯一确定的行为差异是**焦点成两层链**（宿主 + `shadowRoot.activeElement`）。克隆是**承重**的（DSH 自家 CSS-module 内容也靠它），不能拿"轻量内容不需要"省掉。⇒ **"所有视图对等"可行**，代价记在「边界带来的新代价」。

## 开放问题（分成三类）

**必须在定契约前知道**：**「还没落地的」那几条**（上面三件已全过，原「还没定的」已裁）。

**接受这个方向之后要背的债（不阻塞）**：边界上的可达性；边界的调试成本；轻量内容的额外开销。

**另案（不属于这个工作）**：两侧散落的层号要不要收敛成一张表。按本模型它变成"**区域之间那张唯一层序表**"的问题；它仍是独立的一件事，塞进来会把它变成布局契约的附属条件。

## 用词

组件级隔离一律用**隔离**（影子根 / 独立浏览上下文），不用"沙箱"——本仓"沙箱"只指 **agent 运行时的执行沙箱**。`docs/architecture.md` §3.1 已同步。
