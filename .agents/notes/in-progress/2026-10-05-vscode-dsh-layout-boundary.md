# Agent Note: 视图的隔离与对等 —— 区域骨架、视图是单位

> **来源**：2026-10-05 讨论。James：「以插件式思维在 layout 上做隔离，如使用 shadow dom」，随后纠正：***整个 ui 框架应该归属于 prac，我们会从 dsh 和 vscode 中借用或借鉴一些现成的组件。***
> **口径来源**：`docs/architecture.md` §3.1、[2026-09-19-architecture.md](../in-progress/2026-09-19-architecture.md)、[2026-09-13-vs-concept-boundary.md](../in-progress/2026-09-13-vs-concept-boundary.md)（"机制不认识来源词"、"容纳单位 = 视图"），以及两条 superseded 的设计（09-15 / 09-16）。

## Problem

prac 的框架声称「区域树、编排、层级、浮层」都归自己（`docs/architecture.md` §3.1）。但只要盒子里的东西**自带全局样式系统、或自带一套浮层模型**，这句话就有一个未定义的空洞：

> **框架对"盒子里的东西"负什么责？**

此前没有原则回答它，于是"能住下"是靠逐处局部处置维持的（一处管几何、一处管样式、一处管浮层锚点）。**这些处置不是病根，病根是没有原则**；它们只是原则缺席时，每个面逐个被临时补上的痕迹。

## 设计

**布局由 prac 拥有**：区域树、编排、层级、浮层都是框架自己的。**视图是布局里的单位，按窗口的方式来管**——独立、可在区域之间移动、各有各的状态。

### 区域是骨架，视图是单位

| 概念 | 是什么 | 职责 |
| --- | --- | --- |
| **区域**（基础区域 / 悬浮层 / 子区域） | **骨架**：可嵌套、可分栏分列（`center` 是这一层的一个区域） | 划分空间、给视图盒子 |
| **视图** | 被摆放、被拖动、被隔离的**单位** | 内容与它自己的内部 |
| **悬浮层** | **顶层的一个区域** | 住被放在它上面的视图（命令、通知，以及被临时放到这里的任何视图）——它的内容按"这一次的呈现"渲染，不进持久化 |

- **视图住在区域里**；进 layout 就是进某个区域，区域给它盒子。
- **视图的拖放 = 在区域之间搬视图**；迁移的单位就是它。**分栏** = 区域再分出一个子区域，子区域里放视图。
- **视图内部没有第二个 stage，也没有自己的区域树**；视图内部只有它自己。
- **视图之间、区域之间都对等**：同一种对象、同一套契约；机制**按注册表成员认识视图，不认识来源**（`2026-09-13` 已裁）。区域之间的差别只在**命名层绑给它的模式集合与默认模式**，不是特权。

### 隔离与对等（对所有视图）

- **所有挂在 layout 中的视图都隔离**：隔离是**结构性质**，不是给某一类内容开的特例（**作用域不止于浮层**）。
- **所有视图都对等**，两层：**边界上对等**——每个都是一样的隔离盒子、同一份契约、同一套保证，没有特权视图、没有例外；**对待上对等**——机制不认识它的来源。
- **框架不伸手进视图内部**：凡要跨边界生效的（主题、焦点、样式），都必须是对所有视图一致的**显式通路**。
- **框架拥有区域，不拥有视图内部**：分栏、拖放、迁移都落在区域这一级——"对等"说的是**每个区域里一视同仁**，不是所有视图长得一样。

### 隔离的保证与形态

- **保证归框架**："每个视图都被隔离"是**框架的事**，不是内容自愿配合的结果——否则它就不是保证。因此**隔离不由视图选择**（否则又出现"我不用隔离"的例外，统一性当场破掉）。
- **形态可以有多种**：按**内容的性质**选实现——DOM 内容用影子域、自成体系的内容用独立浏览上下文（webview 本来就是这一种），将来还可能有别的。**形态是实现，不是契约**。
- **形态的选择权在框架**：选哪种由**框架**按内容决定，并把结果**记录在视图的身份里**（持久化与调试都要知道它是哪一种）。内容不需要知道，也不需要声明。
- **盒子是硬边界，由框架强制**：宿主同时是绝对**与**固定定位后代的包含块，并裁到盒内 ⇒ **视图画不到自己的盒子外面**。要出现在盒外的，只能走框架的悬浮层。这条是 G3 的强制手段（见「边界带来的新代价」）。
- ⇒ 契约只有一句：**"你被隔离，且我的接口对所有隔离形态一致。"** 上面那张不变量表（G1–G3）就是这个接口的形状。

### 布局模式与区域名绑定

**区域的模式作用于「孩子」；孩子可以是视图或区域：**

| 孩子是 | **顺序**（`stack`，依次） | **选择**（`tab`，选一） | **分区**（并排） |
| --- | --- | --- | --- |
| **视图** | 依次排开（各自可折叠） | 只显示一个 | —— |
| **区域** | —— | 只显示一个——**容器就是这样** | 各占一块（分栏） |

- **叠放只在悬浮层**：叠放 = 同时可见 + **需要定序**；基础层里同时可见的只有分区的各块，而它们互不重叠、不需要定序。**选择**同一时刻只显示一个 ⇒ 定序没有对象 ⇒ 它不是叠放。
- **基础层不需要 z 序**："现在显示哪一个"是**选中**的问题——它是布局的**状态**（持久化），走注意力只是**改变它的交互过程**。
- **框架的装饰单列**：sash、拖拽落点提示、焦点环这类画在内容之上的东西，是**框架自己的装饰**，与内容不同类、不参与内容层序（防止"反正有东西画在上面"被拿来当理由，把内容叠放引回基础层）。

**容器 = 一个具名子区域，与兄弟之间"选一"**（James 2026-10-06）：VS Code 的容器（Explorer / Search / SCM / Run）**不是一个新对象**——它是"选择"区域下的一个孩子区域，名字来自来源目录。**activity bar 的图标条不继承**，切换的载体是**区域头部的容器条**。没有真容器的视图 = "选择"区域下只装它自己的子区域（与 VS Code"给它生成一个容器"同构）。

**区域 = 一组视图或一组子区域，模式由"命名区域"绑定：**

| 区域（位置） | 孩子 | 模式 |
| --- | --- | --- |
| `left` / `right` | 视图；借来的容器（具名子区域） | 容器之间**选择**；容器内**顺序** |
| `center` | 视图；分区出来的子区域 | **选择**（tab），子区域可**分区** |
| `bottom` | 视图；借来的容器 | **选择**（tab） |

**区域是位置，角色是角色——两者分开**（VS Code 自己就是这么分的：`workbench.sideBar.location` 让 primary 侧栏可以放左或放右）：

| 角色 | 绑到谁 | 借的是谁的名 |
| --- | --- | --- |
| `primarySidebar` | DSH 的 `dsh:sidebar` | VS Code ：Primary Side Bar |
| `secondarySidebar` | DSH 的 `dsh:rightbar` | VS Code ：Secondary Side Bar（`ViewContainerLocation.AuxiliaryBar`） |

- **机制提供模式集合**（它认识 `stack` / `tab` / 分区）；**区域名绑定"可用哪些 + 默认哪个"**。两者分开，所以"区域对等"与"各区域不一样"不再打架；**这张表是数据，不是特权**。
- **两个层次要分清（落地时容易混）**：**角色**是 prac 的词，用**平台的角色名** `primarySidebar` / `secondarySidebar`（`RoleBindings`，代码里已改）——位置中立，因为 VS Code 允许 primary 侧栏换边；**区域 id** 是**位置**词 `left` / `right`（不改，改它要升持久化 key）；**借来的名字不动**（`dsh:sidebar` 是 DSH 那个叫 `sidebar` 的槽、`vscode:sidebar` 指 VS Code 的 sidebar、`workbench.parts.sidebar` / `workbench.parts.auxiliarybar` 是 VS Code 部件 id）。
- **区域名是设计层的名字，与来源无关**：`left` / `right` / `center` / `bottom` 是**位置**；DSH 那边的槽名（`sidebar`）与 VS Code 那边的部件 id（`workbench.parts.sidebar`）是**借来的名字**，不在这一层出现。
- **每个子区域跟随它所在区域名的绑定**（`center` 拆出来的每块都有 `tab`、都不能 `stack`）。
- **tab 是区域级的**，不是 center 专有。
- **一个派生要求**：视图在区域之间搬时，**目标区域可能不支持它来源处的模式**；这要求**视图的呈现与它所属的分组解耦**——分组决定怎么显示，视图只管内容。不成立的话，视图就不能真正自由搬运。

### 不继承 VS Code 的布局复杂度

VS Code 的布局树比我们的大（primary sidebar 里还有 activity bar、它的 position 有 top/bottom/hidden；一个 sidebar 有**多个 tab、tab 里再是 stack**；bottom 是 **Panel**，位置能绕 editor 的 top/left/right/bottom）。**分类之后大半不必继承**：

| VS Code 的东西 | 它其实属于 | 我们的处理 |
| --- | --- | --- |
| activity bar 及其 position、sidebar 的 tab 套 stack | **借用件的内容**（容器树） | 不继承——它在那个视图**盒子里**（隔离之后更是如此） |
| primary / secondary sidebar | **角色** | 借它的**名**（`primarySidebar` / `secondarySidebar`） |
| 两个侧栏一左一右 | **位置** | 已有：区域 `left` / `right` |
| Panel 的 top/left/right/bottom | **摆放** | 不需要 `panel.position` 这个概念——**把那个视图搬到别的区域**就行（任意方向分栏已支持） |

⇒ VS Code 的复杂仍然是复杂，但它**留在盒子里**，不是我们布局模型的复杂度。**唯一需要时再加的是"一级还是两级"**：我们机制现在只有一级（区域内 `tab` **或** `stack`），而借用件自带的那层（tab 套 stack）在盒内；我们自己的视图又少又平，**没有真实需求就不加第二级**。

### 视图的状态

- **"选中"是 UI 状态，属于持久化**（它归框架，不归注意力）。
- **持久化按"放置"分**：放在**基础区域**里的视图——区域、组内顺序、折叠、在屏、每个组的选中项、区域用的模式——**进持久化**；放在**悬浮层**里的（锚点、层序、显隐）是**这一次的呈现**，**不进**。**不该有的**：注意力栈、返回栈。
- **条目离开目录时要剪状态**：视图离开目录（一个文件被关掉；一个扩展的视图因 `when` 不再成立而消失）时，框架要**释放它的宿主**，并**剪掉它在持久化里的位置 / 顺序 / 选中**——否则会留下幽灵状态。

### 借用件的 adaptor

**框架只提供隔离本身，不认识任何来源词**。VS Code 那一侧的专有知识——`monaco-workbench` 类、`--vscode-*` 变量、VS Code 样式表、它自己的浮层模型——**全部收在 `vscode-host` 这一层**（机制侧落在 `vendor/vscode-embed`，政策在插件行）：

- **框架侧**：给每个视图一个盒子、一个隔离边界（影子根），到此为止。**它不知道里面是 VS Code**，也不需要"沙箱槽"这类特殊槽——**就是普通槽 + 宿主元素**。
- **adaptor 侧**：把 VS Code 那几样东西投进边界内——**规则表照原样投**、**主题变量以 `:host` 作用域投**、**借用件的宿主元素带 `monaco-workbench` 类**（三者缺一不可，见下）。**浮层按谁创建分**：由**应用自己的服务**创建的面（上下文视图即菜单、命令面板、通知、悬停、模态）**进框架的悬浮层**；由**视图部件自己在自己 DOM 里**画的面（补全列表、webview 的 overlay）**是视图的内部**——同树、自闭环，也正是 CSS 锚点能用的前提（实验 7：锚点在影根里、浮层在文档里 → 不解析）。桥的三条路要分清：整部件走 `partHost`（宿主带 `[data-vscode-embed-part-host]`），VS Code 的**视图**（explorer 等）走 `mountViewInto`（宿主是 `[data-vscode-embed-view]`），**应用自己的根**走 `floatHost`（宿主带 `[data-vscode-embed-float-host]`，机制包把它注册进框架的 `shell.overlay`）。
- **只投规则表还不够：VS Code 的视图 CSS 大多挂在 `.monaco-workbench` 下**。框架**故意不把**这个类放在隔离宿主上（那是另一回事：放在**文档里的宿主**上会让规则作用到宿主本身与其祖先，整屏变样——实测过），于是被镜像进影根的规则**一条也匹配不上**：Outline 的 `display:flex`、`.outline-message{display:none}`、`.outline-tree{height:100%}` 全部落空，表现是**消息常驻 + 树按内容撑高**（实测 734px 的区域里树高 7612px）。修法是**在隔离根内部**给借用件自己的宿主元素带上这个类：作用域仍被影根挡住（实测影根外盒子一个没变），而 VS Code 规则恢复了它们的上下文。⇒ 规则表是**条件**，宿主上的语境类也是。
- **adaptor 与框架之间没有显式接口**：框架给盒子与边界，adaptor 从元素自己认它的根（`getRootNode()`）——根就长在元素上，再加一条"谁告诉谁"的边只是多一层；等出现第二个 adaptor 再抽。
- **借用件的浮层就在框架的悬浮层里**：工作台自己的根**住在**框架的 `shell.overlay`（不是与框架并排的第二个层）——部件早被搬进各视图，跟着根走的只有"应用自己创建的面"。根因此拿到**框架的盒子**（浮层几何全部由它算出：命令面板是 `0.62 × 容器宽`），根与它没放行的东西**点击穿透**，浮层容器逐类放行。「局部浮层进视图自己的根、全局交给框架」这半已落地；**菜单与悬停也在这层里**（实测：那是应用的 `contextViewService` / hover 服务创建的，不是视图部件）。
- ⇒ **机制不做特例，来源词也不外溢**：`monaco-workbench` 从"宿主侧要镜像的类"变成**adaptor 内部的事**。

### 一种视图，一组属性

**prac 里只有一种可显示的东西：视图**（像窗口管理器里只有窗口）。它怎么渲染，由**一组属性**决定——不是由"它属于哪一类视图"决定。

| 属性 | 取值 | 持久化 |
| --- | --- | --- |
| **放置** | 某个基础区域 / **悬浮层** | **按放置分**（见「视图的状态」） |
| **排布** | 顺序、折叠、尺寸、选中（组内在前的那个） | 在基础区域里 ⇒ 进 |
| **呈现** | 在屏、锚点（在悬浮层且要贴锚点时）、层序 | 在悬浮层里 ⇒ **不进**（那是"这一次"） |
| **寿命** | 常驻 / **一次交互**（`transient`） | 是**属性**，不是类 |

- **"浮层视图"描述的是放置，不是类**：右键菜单、命令面板、通知是**被放在悬浮层的视图**；工具提示、补全列表、就地小浮层是视图**盒内的自闭环**。
- **视图可以在区域与悬浮层之间搬**——宿主只有一个，悬浮层只是另一个目的地；搬过去不改变它的身份。
- **预览**（如编辑器的预览标签）是条目上的一枚**旗标**；**动态进出目录**（编辑器随打开的文件来去）是**目录条目的来去**——都不是第三个类。
- **框架 chrome 是唯一的例外**：sash、拖拽落点提示、焦点环不是视图，是框架的装饰。

**要守住的两条**：① **属性分两类**（持久的排布 / 这一次的呈现），混了就会出现"重启后弹出上次的菜单"；② **装饰始终不是视图**。

**与这些设计冲突、已作废的说法**：按内容性质或来源给视图分类；**按"常驻 / 即显即隐"给视图分类**（只有一个东西 + 一组属性）；"区域与悬浮层是两类东西"；"容器既给几何、又是被摆弄的单位"；"tab 是 center 的能力"；"选中归注意力、因此不持久化"；"**右键菜单这类界面不是视图、可以留在视图的盒子里**"。

## 主命题与三条不变量

> **layout 给每一个视图一个隔离盒子，并且所有视图对等。**

| # | 不变量 | 谁保证 | 状态 |
| --- | --- | --- | --- |
| G1 | 每个视图有真实几何（有尺寸，且随区域变化） | 框架（区域） | 未声明 |
| G2 | 视图里的样式出不了它的盒子，也不因缺上下文而失效 | 框架的边界（统一） | 未声明 |
| G3 | **凡"生在 A、要出现在 B"的东西，走显式通路，由 B 落位与定序；视图不能自己画到外面** | 框架（盒子的硬边界） | 已由框架强制 |

**G2 需要 G1 才能成立，G3 需要 G1 与 G2 一起。** 这解释了为什么逐处处置总是按下葫芦浮起瓢：几何没给对时，样式与浮层的问题会被伪装成"样式没进来"或"浮层不见了"（命令面板那次，现象是"打不开"，根因是几何）。

**层级两段，选中独立**：**区域之间的层序**归框架（基础区域与悬浮层之间只有这一张表）；**视图内部的层序**归视图自己；**选中**是第三件事——点一下不改变层序。三者分开：**层序持久化、选中也持久化，而"走神去看了什么"（注意力 / 返回栈）不持久化。**

## 这一轮定下的

- **隔离形态的对应规则**：契约只承诺**"框架保证隔离，且接口对所有形态一致"**（见"隔离的保证与形态"）；形态规则表**等第二种形态真出现再写**。现在落地的只有影子根，webview 本来就是独立浏览上下文、框架不用动作。逐根投放的配方是四件事：① **规则表照原样投**（document 的规则不作用于影子树）；② **主题变量以 `:host` 作用域投**（**不要**把 `monaco-workbench` 放在**宿主本身**上：那会让规则作用到宿主，实测画面整体变样）；③ **借用件的宿主元素在根内带 `monaco-workbench`**（缺它则所有挂在该类下的视图规则失效——2026-10-07 实测：Outline 消息常驻、树撑到 7612px）；④ **活的订阅**，不是死拷贝（主题那张表被原地改写）。都便宜，且不需要 VS Code 补丁。
- **哪些界面由框架创建**：判据是**谁创建**——由**应用自己的服务**创建的（上下文视图即菜单、命令面板、通知、悬停、模态）归框架的悬浮层；由**视图部件在自己的 DOM 里**画的（补全列表、webview 的 overlay）归**视图自己**（自闭环）。
- **坐标空间：借用件的浮层共用框架悬浮层的坐标**。判据不是"有没有锚点"：应用的菜单与悬停**有锚点但也在那一层里**（它们由应用的 `contextViewService` / hover 服务创建，与命令面板同源）；它们按**视口坐标**定位，而该层就是框架的盒子，所以落位正确。**框架自己创建锚点类浮层**（跨视图锚定）仍**先不做**——锚点矩形 + 失效/跟随规则等真出现"必须跨视图锚定"的面再引入。
- **盒子是硬边界**：视图内部的面**不能越出盒子**（框架裁）。所以"越出盒子"不是视图的选项，而是一个**需求**——真需要时它必须走框架的悬浮层，那时才跟坐标空间打交道。
- **这类视图叫浮层视图**——它描述的是**放置**，不是类（见「一种视图，一组属性」）。
- **adaptor 与框架之间没有显式接口**：adaptor 从元素自己认根。

## 还没落地的

- **框架的锚点通路**（锚点矩形 + 落位 / 失效 / 跟随）：被"盒子是硬边界"逼出来的那条路，但按上面的裁决**先不做**；等真出现必须跨视图锚定的面再说。**已有的一层不依赖它**：应用自己的浮层用视口坐标定位。
- **层里的次序**：应用的根在 `shell.overlay` 里以 `order` 排在框架自己的两个面之前（框架的面在上），目前只有这一条；框架自己再长出浮层时，层的次序表要一起写（现在是"框架的面在上"这一句，不是表）。
- **视图内部浮层的逐个归类**：判据已定（谁创建），落到具体面时逐个归即可。

## 菜单、命令面板、通知：由框架提供机制

这类界面**也是视图**（见「一种视图，一组属性」），只是**由框架按需创建**——**不是一种新东西**。视图不该各自造一套菜单：既不可能一致，也拿不到平台该给的东西。

**框架提供的是"怎么显示"的机制**，不是内容：视图（或它内部的元素）只**声明**（菜单项 / 命令 / 通知），**呈现统一归框架**——定位、翻转与贴边、关闭（点外 / Esc / 失焦）、键盘可达、层序。

**先例**：VS Code 与 Chrome 的右键菜单都不是自己画的——它们用 **macOS 系统提供的菜单**（同一条路在别处映射到平台的菜单实现）。"菜单"是**平台 / 宿主**该提供的东西。

**锚点不是"跨视图通路"，是一个位置参数**：框架在悬浮层里创建这个视图，位置用框架的坐标算出来。**框架自己创建锚点类浮层仍先不做**（居中 / 贴角已有）；借用件自己的锚点类浮层（菜单、悬停）**跟着应用的根一起在那一层里**，用视口坐标定位——它们不需要框架的锚点通路。**框架级的跨视图锚定等真出现那个面再引入。**

**借用件里由应用服务创建的那些都在这一层里**：命令面板、上下文视图（菜单）、通知、模态、悬停——它们与视图同处一个悬浮层，因此**不被任何视图的盒子裁**（框架的盒子仍裁）；**只在视图部件自己 DOM 里画的（webview 的 overlay、补全列表）留在视图内**——那不是"自绘一套菜单"，而是视图的内部（同树才能锚定，实验 7）。

## 边界带来的新代价

- **每个视图都付边界成本**：调试多展开一层；可达性结构会变（焦点成两层链）；样式"广播式生效"没了。以前只有"重"的视图付，现在轻量的也付——**实测的形态是每个视图一整份 head 的样式重复（122 节点 / 653 KB）**，CPU 可忽略。**这是"对等"的代价，也是它的价值**（没有第二种规矩）。
- **主题与样式必须走显式通路**：把"样式怎么流"从"碰巧能继承"升级成**契约**。
- **`prac.view` 的含义扩了**：原来只表示"装一个视图宿主"，现在还要携带它在布局里的身份与边界。这是视图契约的实质扩张。
- **盒内浮层只能在盒内翻**：盒子是硬边界（框架裁），所以"浮层越出盒子"不是视图自己能解决的事——要么就地翻转、夹在盒内，要么走框架的悬浮层。借用件那些默认会越界的局部面（窄盒里的菜单）因此要 adaptor 参与。

## 契约写死之前必须先验的三件（已全过）

1. **主题与样式能跨过统一隔离边界**：`:root` 级变量继承、外层类上的不继承、document 规则不作用于影子树；真部件与真 rig 上的视图宿主搬进影子根都**像素零差**；换主题是**原地改写**源表，**盯源表重投**跟得上（零补丁），且**真的切一次主题时画面跟着变**。配方：**规则表照原样投、变量以 `:host` 作用域投**（不用 `monaco-workbench` 包装——实测它会唤醒整条级联、画面整体变样），**活的订阅**。两条挂载路都验过（视图路在真 rig，整部件路在独立查看页 + rig 补验）。
2. **区域有真实几何时，进入悬浮层的东西自然落对**：命令面板那次的根因就是几何（工作台自己的容器是 0×0），**修法是把应用的根放进框架的悬浮层、并让那一层给出盒子**；命令面板随后按 `0.62 × 层宽` 自己算出宽度（实测 600px 上限）、渲染出 19 行并可打字过滤，菜单与悬停同样落对。⇒ 浮层落位不是"放哪"的问题，是**几何**的问题；**另加一条**：几何换了还得让浮层**知道**几何换了——应用的重排挂在 `onDidLayoutContainer` 上，这条事件不补上，改尺寸后浮层不会重排。
3. **统一隔离对轻量内容的实测代价**：代价是**样式在 DOM 里的线性重复**——每个视图一整份 head（默认编排下 **122 个样式节点 / 653 KB / 13,502 条规则**，每多一个视图严格 +1 份）；**CPU 代价可忽略**（镜像亚毫秒、同步一帧内、挂载十几毫秒）；**可达性与键盘未被破坏**（a11y 树穿透影根、首次 Tab 即进根），唯一确定的行为差异是**焦点成两层链**（宿主 + `shadowRoot.activeElement`）。克隆是**承重**的（DSH 自家 CSS-module 内容也靠它），不能拿"轻量内容不需要"省掉。⇒ **"所有视图对等"可行**，代价记在「边界带来的新代价」。

> **栈的行为另立一条 note**：这一节原来写在这里，但它是一个独立的工作（行为定义 + 三处互斥选择），见 [2026-10-15-ui-layout-stack.md](2026-10-15-ui-layout-stack.md)。本 note 只保留"区域可以按 `stack` 模式同时显示多条视图"这条设计。

## 开放问题（分成三类）

- **栈内高度有"两个权威"**：视图记录里的 `ViewRecord.size`（人拖的、折叠时记下的）与渲染期分配器**画出来**的值（`allocateStack`）可以不一致——现场见过"布局里存 69、屏幕上画 519"。它是**布局模型的一致性问题**，与"给区域补 `max`/`priority`/`Sizing`"（见 [../proposed/2026-10-15-ui-layout-grid.md](../proposed/2026-10-15-ui-layout-grid.md)）**不是同一件事**。两条候选解法：① 分配结果**写回**视图记录（曾试过，未收敛）；② 把**栈变成树的结构**（栈 = 一个 `column` branch，每条 = 一个叶子 ⇒ 高度只剩树一个权威）——后者是一次模型重构，要单独裁。

**必须在定契约前知道**：**「还没落地的」那几条**（上面三件已全过，原「还没定的」已裁）。

**接受这个方向之后要背的债（不阻塞）**：边界上的可达性；边界的调试成本；轻量内容的额外开销。

**另案（不属于这个工作）**：两侧散落的层号要不要收敛成一张表。按本模型它变成"**区域之间那张唯一层序表**"的问题；它仍是独立的一件事，塞进来会把它变成布局契约的附属条件。

## 用词
- **"上游"必须写明是哪一个**：**DSH**（平台与契约：`dsh.bundle` / `dsh.profile` / `cordis.patch.yml`、注入的服务 `slots` / `theme` / `uiSession`、`client-store` 的快照引擎与启动种子、四个区域槽位）——它是**地基**，不可违背；**VS Code**（借用的 UI 与行为：`SplitView` / `Grid` / workbench parts）——它是**行为与手感的来源**，prac 重写某段借用行为时对齐它。两者冲突时以 **DSH 契约**为准。

组件级隔离一律用**隔离**（影子根 / 独立浏览上下文），不用"沙箱"——本仓"沙箱"只指 **agent 运行时的执行沙箱**。`docs/architecture.md` §3.1 已同步。
